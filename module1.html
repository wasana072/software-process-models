Section 01 // Foundations

ซอฟต์แวร์ไม่ได้มีแค่โค้ด: นิยามและขอบเขตของวิศวกรรมซอฟต์แวร์

นักศึกษาวิทยาการคอมพิวเตอร์มักคุ้นเคยกับการเขียนโปรแกรมเพื่อแก้โจทย์รายวิชาด้วยตัวคนเดียว แต่ในโลกอุตสาหกรรม ซอฟต์แวร์ระดับมืออาชีพ (Professional Software) ถูกสร้างขึ้นเพื่อให้ผู้อื่นใช้งาน พัฒนาร่วมกันเป็นทีม และต้องดูแลปรับปรุงต่อเนื่องตลอดอายุการใช้งาน ดังนั้นคำว่า “ซอฟต์แวร์” ในทางวิศวกรรมจึงไม่ได้หมายถึงเพียงตัวโปรแกรม (Computer Programs) แต่รวมถึงเอกสารระบบ (System Documentation) คู่มือผู้ใช้ (User Documentation) ไลบรารี ข้อมูลการตั้งค่า (Configuration Data) และระบบสนับสนุนที่ทำให้ซอฟต์แวร์นั้นทำงานได้อย่างสมบูรณ์

1.1 เปรียบเทียบระดับขอบเขต: Programming vs. Development vs. Engineering

ตามกรอบแนวคิดของ Dooley & Kazakova (2024) และ Sommerville (2016) เราสามารถแบ่งขอบเขตงานออกเป็น 3 ระดับที่ซ้อนทับกัน และเทียบเคียงกับศาสตร์ข้างเคียงอย่าง Computer Science และ Systems Engineering ได้ดังตารางต่อไปนี้

แนวคิด / ศาสตร์ จุดเน้นหลัก (Core Focus) ขอบเขตความรับผิดชอบ
Programming การแปลงอัลกอริทึมเป็นโค้ด เป็นเพียงส่วน Implementation หรือส่วนหนึ่งของการออกแบบและเขียนโค้ด (Coding & Debugging)
Software Development การสร้างตัวผลิตภัณฑ์ซอฟต์แวร์ รับความต้องการจากผู้ใช้ วิเคราะห์ ออกแบบ เขียนโค้ด ทดสอบ และปล่อยรุ่น (Requirements → Release)
Software Engineering การผลิตอย่างเป็นระบบภายใต้ข้อจำกัด ครอบคลุม Software Development ทั้งหมด บวกกับ การบริหารโครงการ การจัดการการเปลี่ยนแปลง (CM) การประเมินต้นทุน-เวลา และการบริหารทีม
Computer Science ทฤษฎีและพื้นฐานการคำนวณ เน้นทฤษฎี โครงสร้างข้อมูล อัลกอริทึม และภาษาคอมพิวเตอร์ ซึ่งมักพิสูจน์ได้ดีในโปรแกรมขนาดเล็ก
Systems Engineering ระบบเชิงสังคม-เทคนิคทั้งองค์กร ออกแบบทั้ง Hardware, Software, นโยบาย (Policy) และกระบวนการทำงานของมนุษย์ (Sociotechnical System)

1.2 ประเภทของผลิตภัณฑ์ซอฟต์แวร์และสัดส่วนต้นทุน

ในมุมมองของการจัดจ้างและการควบคุมความต้องการ ผลิตภัณฑ์ซอฟต์แวร์แบ่งออกเป็น 2 กลุ่มหลัก:

  • 1. Generic Products (ผลิตภัณฑ์ทั่วไป) — ระบบแบบ Stand-alone ที่องค์กรพัฒนาเพื่อวางขายในตลาดเปิด เช่น แอปพลิเคชันมือถือ โปรแกรมฐานข้อมูล โปรแกรมสำนักงาน หรือระบบเฉพาะทางสำหรับตลาดเฉพาะกลุ่ม (เช่น ระบบคลินิกทันตกรรม) ผู้พัฒนาเป็นผู้ควบคุม Specification หากติดปัญหาสามารถปรับขอบเขตฟีเจอร์ได้
  • 2. Customized / Bespoke Software (ซอฟต์แวร์สั่งทำเฉพาะ) — ระบบที่พัฒนาขึ้นตามคำสั่งของลูกค้าเฉพาะราย เช่น ระบบควบคุมอุปกรณ์อิเล็กทรอนิกส์ หรือระบบควบคุมการจราจรทางอากาศ ลูกค้าเป็นผู้กำหนดและควบคุม Specification ทีมพัฒนาต้องสร้างให้ตรงตามข้อกำหนดนั้น

แนวโน้มแบบลูกผสม (Hybrid ERP Systems)

ปัจจุบันเส้นแบ่งทั้งสองเริ่มเลือนลง ระบบองค์กรขนาดใหญ่จำนวนมาก (เช่น SAP หรือ Oracle ERP) ใช้ Generic Product เป็นฐาน แล้วนำมาปรับแต่ง (Configure) กฎทางธุรกิจและรายงานให้เข้ากับลูกค้าเฉพาะราย

โครงสร้างต้นทุนซอฟต์แวร์ (Sommerville Fig 1.1)

สัดส่วนค่าใช้จ่ายก่อนส่งมอบระบบ (Pre-delivery Cost) โดยทั่วไปของโครงการซอฟต์แวร์:

DEV 60%
TEST 40%

ข้อสังเกตสำคัญ: สำหรับระบบ Custom Software ต้นทุนในระยะวิวัฒนาการและบำรุงรักษาหลังส่งมอบ (Evolution Costs) มักสูงกว่าต้นทุนการพัฒนาเริ่มต้น (Development Costs) เพราะระบบต้องถูกปรับเปลี่ยนตามสภาพแวดล้อมทางธุรกิจตลอดหลายปี

1.3 คุณลักษณะ 4 ประการของซอฟต์แวร์ที่ดี (Essential Software Attributes)

คุณภาพของซอฟต์แวร์ไม่ได้วัดแค่ “ทำงานได้ตรงฟังก์ชัน” (Functional) เท่านั้น แต่รวมถึงพฤติกรรมขณะรันและโครงสร้างโค้ดที่ผู้อื่นต้องมาดูแลต่อ (Non-functional Attributes) คลิกที่การ์ดเพื่อดูรายละเอียดเชิงลึก:

เจาะลึก: Maintainability (การบำรุงรักษาได้)

เป็นคุณลักษณะที่สำคัญที่สุดในระยะยาว เพราะสภาพแวดล้อมทางธุรกิจเปลี่ยนแปลงตลอดเวลา หากระบบมี Modularity ที่ดี มีการห่อหุ้มข้อมูล (Encapsulation) และมีเอกสารประกอบครบถ้วน ทีมวิศวกรรุ่นถัดไปจะลดต้นทุน Evolution ได้อย่างมหาศาล

ขยายความ: 4 ความท้าทายยุคใหม่ & จริยธรรมวิชาชีพวิศวกรซอฟต์แวร์ (ACM/IEEE Code of Ethics)
4 ความท้าทายหลักของซอฟต์แวร์สมัยใหม่ (Sommerville 1.1.1)
  • Heterogeneity: ระบบต้องรันข้ามแพลตฟอร์ม ทั้งมือถือ แท็บเล็ต คลาวด์ และต้องเชื่อมต่อกับระบบเก่า (Legacy Systems) ที่เขียนด้วยคนละภาษา
  • Business & Social Change: ธุรกิจและเศรษฐกิจเปลี่ยนแปลงเร็ว กระบวนการพัฒนาจึงต้องลดเวลาส่งมอบคุณค่า (Time-to-value)
  • Security & Trust: ซอฟต์แวร์เชื่อมโยงกับทุกมิติของชีวิต การเข้าถึงผ่านเว็บและ API ต้องป้องกันผู้ไม่หวังดีได้
  • Scale: ตั้งแต่ระบบฝังตัวขนาดเล็กมาก (Embedded/Wearable) ไปจนถึงระบบคลาวด์ระดับโลก
ความรับผิดชอบทางจริยธรรม 4 ด้าน & 8 หลักการ ACM/IEEE
  • 4 กรอบความรับผิดชอบที่กฎหมายไม่ได้ระบุทั้งหมด: Confidentiality (รักษาความลับ), Competence (ไม่รับงานเกินขีดความสามารถ), Intellectual Property Rights (เคารพสิทธิบัตร/ลิขสิทธิ์), Computer Misuse (ไม่ใช้ทักษะในทางมิชอบ)
  • 8 หลักการ (ACM/IEEE Code of Ethics): 1. Public (ประโยชน์สาธารณะ) · 2. Client & Employer · 3. Product · 4. Judgment · 5. Management · 6. Profession · 7. Colleagues · 8. Self (เรียนรู้ตลอดชีวิต)
Section 02 // Software Process & SDLC

วงจรชีวิตการพัฒนาระบบ: 4 กิจกรรมพื้นฐานสู่ 8 ระยะของ SDLC

Software Process คือชุดกิจกรรมที่สัมพันธ์กันเพื่อนำไปสู่การผลิตซอฟต์แวร์หนึ่งระบบ Sommerville (2016) สรุปว่าไม่ว่าจะใช้โมเดลกระบวนการแบบใด ทุกกระบวนการต้องมี 4 กิจกรรมพื้นฐานร่วมกัน ได้แก่ (1) Software Specification กำหนดความต้องการและข้อจำกัด, (2) Software Development ออกแบบและเขียนโปรแกรม, (3) Software Validation ทวนสอบว่าตรงตามที่ลูกค้าต้องการ และ (4) Software Evolution ปรับเปลี่ยนระบบตามความต้องการใหม่

เมื่อนำกิจกรรมเหล่านั้นมาคลี่เป็นลำดับขั้นตอนปฏิบัติใน Software Development Lifecycle (SDLC) ตามตำราของ Dooley & Kazakova (2024) จะประกอบด้วย 8 ระยะหลักตั้งแต่แนวคิดเริ่มต้นจนถึงการปลดระวางระบบ ลองสลับโหมดการดำเนินงานด้านล่างและคลิกที่แต่ละระยะเพื่อสำรวจเป้าหมาย เงื่อนไข และสิ่งที่ต้องส่งมอบ

รูปแบบ Plan-Driven (Sequential Cascade)

วางแผนและจัดทำเอกสารครบถ้วนในแต่ละระยะ (Sign-off) ก่อนส่งต่อไปยังระยะถัดไป เหมาะกับระบบที่ข้อกำหนดชัดเจนหรือมีความเสี่ยงด้านความปลอดภัยสูง

คลิกเลือกระยะของ SDLC (1–8) เพื่อเปิดดูรายละเอียดกิจกรรมและ Artifacts

Section 03 // Process Artifacts & Governance

ผลผลิตในกระบวนการ: Artifacts, Roles, เงื่อนไข และมาตรฐานคุณภาพ

เมื่ออธิบายกระบวนการซอฟต์แวร์ในระดับมืออาชีพ เราไม่พูดถึงแค่ “ใครทำอะไร” แต่ต้องระบุองค์ประกอบกำกับ 3 อย่างเสมอ (Sommerville Ch 2): 1) Products / Deliverables (ผลลัพธ์ที่เป็นรูปธรรมของกิจกรรม เช่น แบบจำลองสถาปัตยกรรม), 2) Roles (บทบาทหน้าที่ของผู้รับผิดชอบ เช่น Project Manager, Configuration Manager, Programmer) และ 3) Pre- and Postconditions (เงื่อนไขที่ต้องเป็นจริงก่อนเริ่มและหลังจบกิจกรรม เช่น ลูกค้าต้องอนุมัติความต้องการก่อนจึงเริ่มออกแบบสถาปัตยกรรมได้)

ข้อควรระวังในการสอบและทำงานจริง: Milestones ≠ Deliverables

ตามคำนิยามใน Sommerville (Ch 23): Milestones คือรายงานความคืบหน้าระยะสั้นสำหรับผู้บริหารใช้ติดตามโครงการ ส่วน Deliverables คือผลผลิตหลักของโครงการที่ส่งมอบให้ลูกค้าตามสัญญา เช่น เอกสารความต้องการ (SRS) หรือระบบซอฟต์แวร์เวอร์ชันแรก

3.1 สำรวจ Process Artifacts ตามกิจกรรมหลัก

ชื่อ Artifact / ผลผลิต กิจกรรมหลัก ผู้รับผิดชอบหลัก (Roles) รายละเอียดและบทบาทในโครงการ

3.2 Product Standards vs. Process Standards (Sommerville Fig 24.4)

เพื่อให้ทีมขนาดใหญ่ทำงานได้สม่ำเสมอและตรวจสอบคุณภาพได้ มาตรฐานในวิศวกรรมซอฟต์แวร์แบ่งออกเป็น 2 ฝั่งคู่ขนานกัน:

Product Standards (มาตรฐานของตัวผลผลิต) Process Standards (มาตรฐานของขั้นตอนการทำงาน)
โครงสร้างเอกสารความต้องการ (Requirements Document Structure) กระบวนการทบทวนแบบ (Design Review Conduct)
แบบฟอร์มทบทวนการออกแบบ (Design Review Form) ขั้นตอนการส่งโค้ดใหม่เข้าสู่ระบบ Build (Submission of New Code)
รูปแบบ Comment Header ของ Method/Class กระบวนการปล่อยเวอร์ชัน (Version Release Process)
แนวทางการเขียนโค้ด (เช่น Java Programming Style) กระบวนการอนุมัติแผนโครงการและควบคุมการเปลี่ยนแปลง (Change Control Process)
แบบฟอร์มคำขอเปลี่ยนแปลง (Change Request Form) ขั้นตอนการบันทึกผลการทดสอบ (Test Recording Process)
Section 04 // Process Models & Trade-offs

ไม่มีโมเดลเดียวที่ดีที่สุด: การเลือก Process Model ให้เหมาะกับระบบ

ทั้ง Sommerville และ Dooley & Kazakova ย้ำตรงกันว่า “ไม่มี Process Model ใดที่ดีที่สุดสำหรับทุกโครงการ” การเลือกโมเดลขึ้นอยู่กับความชัดเจนของความต้องการ ความวิกฤตด้านความปลอดภัย (Safety/Security) ข้อจำกัดของฮาร์ดแวร์ ขนาดและประสบการณ์ของทีม รวมถึงกรอบเวลา ในทางปฏิบัติ โครงการขนาดใหญ่มัก ผสมผสานหลายโมเดล (Hybridize) เช่น ส่วนที่เชื่อมฮาร์ดแวร์หรือมีกฎหมายกำกับใช้ Plan-driven ส่วนที่เชื่อมต่อกับผู้ใช้และต้องการการทดลองใช้ Incremental / Agile

เปรียบเทียบคุณลักษณะ 5 Process Models (คะแนนเชิงเปรียบเทียบ 1–5)
สรุปจุดแข็งและเงื่อนไขการใช้งานแต่ละโมเดล
  • Waterfall (Plan-driven): ดีเมื่อความต้องการนิ่ง, เป็น Embedded ที่ผูกกับฮาร์ดแวร์, เป็น Safety-critical system ที่ต้องวิเคราะห์ก่อนเขียนโค้ด, หรือมีหลายบริษัททำคนละ Subsystem
  • Incremental Development: พัฒนาและส่งมอบทีละส่วน รับ Feedback เร็ว แต่ถ้าเพิ่มฟีเจอร์เรื่อย ๆ โดยไม่ Refactor โครงสร้างระบบอาจเสื่อมสภาพได้
  • Agile / Scrum: ส่งมอบทุก 2–3 สัปดาห์ ใช้ Product Backlog และ User Stories ลดเอกสารทางการ เหมาะเมื่อทีมสื่อสารใกล้ชิดและ Requirements เปลี่ยนบ่อย
  • Reuse-oriented (Integration & Configuration): ค้นหา COTS / Open-source / ERP มาปรับแต่ง ลดเวลาและต้นทุน แต่ต้องยอมประนีประนอมบาง Requirement
  • Spiral Model (Boehm): วนเป็นเกลียวโดยทุกรอบมีการประเมินและลดความเสี่ยง (Risk-driven) เหมาะกับโครงการขนาดใหญ่ที่เสี่ยงสูง

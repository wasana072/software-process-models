Module 01

Foundations of Software Engineering & SDLC

เนื้อหาบทเรียน เอกสารประกอบการสอน และกิจกรรมปฏิบัติการ สำหรับนักศึกษาปริญญาตรี

1

นิยามและความสำคัญของ Software Process & Modeling

  • Software Process: ชุดกิจกรรม (Activities), บทบาทหน้าที่ (Roles), และผลลัพธ์ (Artifacts) ที่เรียงต่อกันอย่างมีระบบ เพื่อสร้าง ปรับปรุง และดูแลรักษาผลิตภัณฑ์ซอฟต์แวร์
  • Software Process Modeling: การสร้างแบบจำลองของกระบวนการเพื่อช่วยในการทำความเข้าใจ วิเคราะห์ ประเมินความเสี่ยง และปรับปรุงการทำงานอย่างต่อเนื่อง
  • Why Process Matters: เป็นกลไกสำคัญในการควบคุมคุณภาพ (Quality), ต้นทุนการผลิต (Cost), และระยะเวลาส่งมอบ (Schedule) ตามสามเหลี่ยมบริหารโครงการ (Triple Constraint)
  • The Engineering Paradox: ซอฟต์แวร์คุณภาพดีไม่ได้เกิดจากความขยันเฉพาะบุคคล แต่เกิดจากกระบวนการพัฒนาที่มีประสิทธิภาพและซ้ำเดิมได้ (Repeatable & Scalable)
💡 Visual / Graphic Idea
แผนภาพ Input-Process-Output (IPO Diagram): แสดงความเชื่อมโยงโดยฝั่งซ้ายเป็น Business Requirements & Constraints นำเข้าสู่กล่องประมวลผล "Software Process Model" (ที่มีองค์ประกอบ People, Tools, Procedures) และส่งมอบผลลัพธ์ปลายทางเป็น High-Quality Software & Artifacts
2

วงจรชีวิตการพัฒนาซอฟต์แวร์ (SDLC Core Phases)

  • 1. Requirements Engineering: การรวบรวม วิเคราะห์ และจัดทำเอกสารข้อกำหนดความต้องการระบบ
  • 2. System & Software Design: การออกแบบสถาปัตยกรรมระบบ (Architecture), โครงสร้างฐานข้อมูล (ERD), และ UI/UX (Wireframes/Prototypes)
  • 3. Implementation (Coding): การพัฒนาโปรแกรมตามข้อกำหนด การเขียน Unit Test และการทำ Code Refactoring
  • 4. Verification & Validation (Testing): การตรวจสอบความถูกต้อง
    • Verification: "Are we building the product right?" (ตรงตามสเปกหรือไม่)
    • Validation: "Are we building the right product?" (ตอบโจทย์ผู้ใช้จริงหรือไม่)
  • 5. Deployment & Maintenance: การนำระบบขึ้นใช้งานบน Production Environment การติดตามผล และการบำรุงรักษาระบบ
💡 Visual / Graphic Idea
แผนภาพวงกลม 5 ขั้นตอน (Circular SDLC Flow Diagram): แสดงสายงานพัฒนาที่เป็นวงรอบต่อเนื่อง พร้อมลูกศรเชื่อมโยงการย้อนกลับ (Feedback Loop) จากเฟส Testing และ Deployment กลับไปยังเฟส Requirements/Design เพื่อปรับปรุงแก้ไข
3

ผลลัพธ์ในแต่ละขั้นตอน (Software Process Artifacts)

  • Requirements Artifacts: เอกสารข้อกำหนดระบบ Software Requirements Specification (SRS), User Stories, Use Case Diagrams
  • Design Artifacts: แผนผัง Architecture Diagram, Database Schema (ERD), API Specifications (OpenAPI / Swagger)
  • Implementation Artifacts: Source Code (Clean Code), Unit Test Suite, Developer Documentation
  • Testing & Deployment Artifacts: Test Cases, Test Summary Reports, Dockerfile, และ CI/CD Pipeline Configuration
  • ความสำคัญของ Artifacts: ช่วยสร้างสื่อกลางความเข้าใจในทีม ลดความเสี่ยงเมื่อเปลี่ยนสมาชิกในทีม และใช้เป็นหลักฐานยืนยันความสมบูรณ์ในแต่ละเฟส
💡 Visual / Graphic Idea
ตาราง Matrix Artifacts Mapping: ตารางเปรียบเทียบ 2 คอลัมน์ ฝั่งซ้ายเป็นขั้นตอน SDLC พร้อมไอคอนประจำเฟส ฝั่งขวาเป็นรายการไฟล์/เอกสาร Artifacts เชิงรูปธรรมที่ต้องส่งมอบในเฟสนั้นๆ
4

การเลือก Process Model (Context-Driven Model Selection)

  • หลักการ "No Silver Bullet": ไม่มี Process Model ใดที่สมบูรณ์แบบที่สุดสำหรับทุกโครงการ การเลือกต้องพิจารณาจากบริบทเป็นหลัก
  • Traditional Models (Waterfall, V-Model): เหมาะกับโครงการที่ Requirements ชัดเจน ความเสี่ยงสูง และไม่เปลี่ยนบ่อย (เช่น ระบบการบิน, ระบบการแพทย์)
  • Iterative & Incremental Models: แบ่งส่งมอบงานเป็นงวดๆ เพื่อลดความเสี่ยงจากการส่งมอบแบบ Big Bang
  • Agile Process (Scrum, Kanban): เหมาะกับโครงการที่มีความเปลี่ยนแปลงสูง ต้องการความเร็ว (Time-to-Market) และรับ Feedback จากผู้ใช้ต่อเนื่อง
  • เกณฑ์การตัดสินใจ: ขนาดทีม, ความซับซ้อนของเทคโนโลยี, ระดับความชัดเจนของโจทย์, และระดับการมีส่วนร่วมของลูกค้า
💡 Visual / Graphic Idea
แผนภาพ Radar Chart / Decision Matrix: เปรียบเทียบ 3 รูปแบบโมเดล (Traditional, Iterative, Agile) ตาม 4 มิติหลัก ได้แก่ Requirement Stability, Project Scale, Risk Tolerance, และ Customer Involvement

Software House Organization, Cross-Functional Roles & Soft-Aware Team Dynamics

1.1 จากการเขียนโค้ดส่วนบุคคลสู่ทีมข้ามสายงาน (Cross-Functional Teams)

Ian Sommerville (2016, บทที่ 1) เน้นย้ำความแตกต่างสำคัญระหว่าง Individual Programming กับ Professional Software Development ว่า ซอฟต์แวร์ระดับอาชีพไม่ได้ถูกเขียนขึ้นเพื่อผู้พัฒนาใช้งานเอง แต่ถูกสร้างโดย ทีมงาน (Teams) เพื่อส่งมอบให้ผู้ใช้กลุ่มอื่น และต้องได้รับการบำรุงรักษาและวิวัฒนาการไปตลอดอายุการใช้งาน ดังนั้น ซอฟต์แวร์จึงไม่ได้หมายถึงเพียงตัวโปรแกรม (Source Code) เท่านั้น แต่รวมถึงเอกสารระบบ เอกสารผู้ใช้ ไลบรารี การตั้งค่า (Configuration Data) และโครงสร้างพื้นฐานที่ทำให้ระบบทำงานได้จริง

ใน Software House ยุคใหม่ การจัดโครงสร้างทีมมักยึดแนวทาง Cross-Functional Self-Organizing Team ที่รวมผู้เชี่ยวชาญหลายบทบาทไว้ในทีมเดียว เพื่อให้สามารถส่งมอบ Product Increment ที่สมบูรณ์และพร้อมใช้งาน (Potentially Shippable Product Increment) ได้โดยไม่ต้องรอส่งงานข้ามแผนกให้เกิดคอขวด บทบาทหลักภายในทีมจำลอง Software House ประกอบด้วย:

VALUE & PRIORITY

Product Owner (PO)

ตัวแทนผู้มีส่วนได้ส่วนเสียหรือลูกค้า มีหน้าที่กำหนด Product Goal เขียนและจัดลำดับความสำคัญของ Product Backlog (ในรูป User Stories) ตรวจสอบให้ทีมเข้าใจบริบทธุรกิจเบื้องหลังแต่ละ Story และกำหนด Acceptance Criteria เพื่อตรวจรับงาน (Dooley & Kazakova, 2024; Sommerville, 2016)

PROCESS FACILITATOR

Scrum Master

ผู้เชี่ยวชาญกระบวนการ Agile/Scrum ทำหน้าที่โค้ชทีมให้ยึดค่านิยม Scrum (Commitment, Focus, Openness, Respect, Courage) เพิ่มความโปร่งใส ขจัดอุปสรรค (Blockers) และปกป้องทีมจากการแทรกแซงภายนอกระหว่าง Sprint ไม่ใช่หัวหน้าหรือผู้จัดการทีม เพราะทีม Scrum ตัดสินใจร่วมกันบนความเท่าเทียม

TECHNICAL DESIGN

Software / Product Architect

รับผิดชอบการออกแบบสถาปัตยกรรมระบบ (Architecture in the Small สำหรับโครงสร้างภายในโปรแกรม และ Architecture in the Large สำหรับระบบองค์กร/บริการกระจายศูนย์) เมื่อโครงการขยายเป็น Multi-team Scrum แต่ละทีมจะมี Product Architect มาร่วมกันกำหนดทิศทางสถาปัตยกรรมภาพรวม (Sommerville Ch. 3, 6)

IMPLEMENTATION

Frontend & Backend Developers

สมาชิกแกนหลักของ Development Team ที่แปลง User Stories เป็น Implementation Tasks ประเมินแรงงาน ออกแบบ API/UI เขียนโค้ดควบคู่การทดสอบระดับหน่วย (Unit Testing / TDD) และร่วมกันถือครองโค้ดทั้งหมดแบบ Collective Code Ownership

QUALITY ASSURANCE

QA / Testing Engineers

ออกแบบ Gray-box Integration Tests ทดสอบจุดเชื่อมต่อระหว่างโมดูล (Dooley & Kazakova Ch. 18) วางแผน Release Testing และทำหน้าที่ตรวจสอบคุณภาพอิสระ (Independent Quality Management) รวมถึงกำกับดูแล Defect Tracking และการทบทวนรหัส (Inspections)

AUTOMATION & OPS

DevOps / Infrastructure Engineers

จัดการ Configuration Management, Automated Build Servers, สภาพแวดล้อม Host-Target Development, CI/CD Pipelines, ความปลอดภัยของ Branch และกระบวนการ Release Management เพื่อให้การ Build และ Deploy เกิดขึ้นซ้ำได้อย่างแม่นยำ (Sommerville Ch. 25)

1.2 การแยกความเป็นผู้นำเชิงเทคนิคออกจากการบริหารจัดการ (Technical vs. Managerial Leadership)

Sommerville (2016, บทที่ 22: Project Management) ชี้ให้เห็นปัญหาคลาสสิกในอุตสาหกรรมซอฟต์แวร์ว่า วิศวกรซอฟต์แวร์ที่เก่งด้านเทคนิคมาก ๆ อาจขาดทักษะด้านการบริหารคน (People Management) และการเจรจากับผู้มีส่วนได้ส่วนเสียภายนอก ในทางกลับกัน ผู้จัดการโครงการที่เชี่ยวชาญด้านงบประมาณและตารางเวลาอาจไม่เข้าใจความซับซ้อนเชิงสถาปัตยกรรมของโค้ด

นอกจากนี้ โครงสร้างทีมแบบลำดับชั้นตายตัว (Hierarchical Groups แบบทหารที่สั่งการจากบนลงล่าง) มักล้มเหลวในงานวิศวกรรมซอฟต์แวร์ที่ซับซ้อนด้วยเหตุผล 2 ประการ คือ (1) การแก้ไขซอฟต์แวร์ส่วนหนึ่งมักกระทบหลายโมดูล จึงต้องการการสื่อสารและต่อรองระหว่างทุกสายงานทุกระดับ และ (2) เทคโนโลยีซอฟต์แวร์เปลี่ยนแปลงเร็วมากจนวิศวกรรุ่นใหม่อาจรู้เครื่องมือสมัยใหม่ดีกว่าผู้บริหารระดับสูง การปิดกั้นการสื่อสารแบบ Top-down จึงทำให้องค์กรพลาดโอกาสทางเทคโนโลยีและทำให้คนรุ่นใหม่หมดไฟ ดังนั้น สำหรับโครงการขนาดกลางถึงใหญ่ ควรแยกบทบาท Project Manager และ System Architect ออกจากกันอย่างชัดเจน:

มิติการเปรียบเทียบ Project Manager (Managerial Leadership) System Architect (Technical Leadership)
ขอบเขตความรับผิดชอบหลัก แผนงานโครงการ (Schedule), งบประมาณ, การวิเคราะห์ความเสี่ยง (Risk Management), การจัดสรรทรัพยากร และการส่งมอบตามสัญญา สถาปัตยกรรมระบบ (Architectural Design), การเลือก Tech Stack, มาตรฐาน API/ฐานข้อมูล, คุณสมบัติไม่พึงประสงค์ (Non-functional Attributes: Security, Reliability, Performance)
การตัดสินใจสำคัญ การปรับขอบเขตงาน (Scope), การจัดการเวลา Sprint/Milestone, การคัดเลือกรูปแบบกระบวนการ (Plan-driven vs Agile/Hybrid) การตัดสินใจเชิงเทคนิคระดับวิกฤต, การแก้ปัญหา Technical Debt, การออกแบบโครงสร้างโมดูล (Tight Integration, Loose Coupling)
จุดเน้นด้านการสื่อสาร ผู้บริหารระดับสูง, ลูกค้า, Product Owner, การรักษาขวัญกำลังใจและความร่วมมือของทีม Developers, QA, DevOps และการประสานงานสถาปัตยกรรมระหว่างทีมย่อย (Product Architects Collaboration)
ข้อควรระวัง ห้ามทำตัวเป็น Back-seat Driver หรือแทรกแซงวิธีเขียนโค้ดของนักพัฒนา (Dooley & Kazakova Ch. 3) ต้องเปิดรับความเห็นของสมาชิกทุกระดับและหลีกเลี่ยงการสร้างคอขวดเชิงความรู้ (Knowledge Silo)

1.3 Soft-Aware Development และพลวัตของทีมวิศวกรรม (Dooley & Kazakova, Ch. 3 & 4)

ดร. เวรา คาซาโควา และ จอห์น ดูลีย์ (2024) นำเสนอกระบวนทัศน์ใหม่ชื่อ Soft-Aware Development ที่วางปัจเจกบุคคล ความสัมพันธ์ระหว่างบุคคล และวัฒนธรรมองค์กรเป็นหัวใจของการสร้างซอฟต์แวร์ที่ยั่งยืน โดยมีแก่นแนวคิดสำคัญว่า “Learning to work together while attempting to make software” สำคัญยิ่งกว่าการเรียนรู้วิธีเขียนซอฟต์แวร์เพียงอย่างเดียว เพราะเทคโนโลยีเปลี่ยนแปลงตลอดเวลา แต่ทักษะ Social-Emotional Learning (SEL) — การรู้จักตนเอง จัดการอารมณ์ แสดงความเห็นอกเห็นใจ สร้างความสัมพันธ์ที่เกื้อกูล และตัดสินใจอย่างรับผิดชอบ — คือรากฐานที่ทำให้งานวิจัยและผลผลิตของทีมเกิดขึ้นได้จริง

Psychological Safety & “Accountable but Blameless”

วัฒนธรรมที่เน้นเฉพาะผลลัพธ์ (Output-only culture) จะทำให้การเรียนรู้และการลองผิดลองถูกกลายเป็นเรื่องไม่ปลอดภัย นักพัฒนาจะเกิดพฤติกรรมหลีกเลี่ยงความเสี่ยง (Risk Aversion) เลือกทำแต่ Task ง่ายๆ เพื่อให้ดูเหมือนทำงานเร็ว และปิดบังปัญหาไว้จนสายเกินแก้ หลักการ Accountable but Blameless (Iqbal, 2023) ช่วยให้ทีมรับผิดชอบต่อความผิดพลาดร่วมกันโดยไม่ชี้นิ้วกล่าวโทษตัวบุคคล เช่น หากเกิด Merge Conflict รุนแรงก่อนวัน Demo ทีมจะไม่ตำหนินักพัฒนาคนเดียว แต่จะทบทวนใน Retrospective ว่าเหตุใดเขาจึงไม่กล้าขอความช่วยเหลือ หรือเหตุใดทีมจึงข้าม Daily Standup จนมองไม่เห็นสัญญาณเตือน

Egoless Programming vs. “Beer Truck Problem”

ในการพัฒนาแบบมืออาชีพ โค้ดไม่ใช่สมบัติส่วนตัวของคนเขียนคนเดียว แนวคิด Collective Code Ownership (Sommerville Ch. 3) และ Egoless Programming กำหนดให้สมาชิกทุกคนมีสิทธิ์และหน้าที่ร่วมกันปรับปรุงและ Refactor โค้ดทุกส่วนในระบบ เพื่อขจัด “Islands of Expertise” (เกาะแห่งความเชี่ยวชาญเฉพาะบุคคล) ซึ่งเป็นต้นตอของ Beer Truck Problem (Bus Factor) — ภาวะที่โครงการต้องหยุดชะงักทันทีหากนักพัฒนาคนสำคัญป่วย ลาออก หรือประสบอุบัติเหตุ การทำ Pair Programming, Code Review และการจัดทำ Documentation ที่เข้าถึงได้ทั่วถึงจึงเป็นการกระจายความรู้อย่างเป็นระบบ

การกำจัด “Dark Scrum” และ Micromanagement (อุปมาการขับรถในภูมิประเทศที่ไม่รู้จัก)

Ron Jeffries เรียกการนำ Agile/Scrum ไปใช้แบบบิดเบือนโดยผู้มีอำนาจสั่งการทุกขั้นตอนว่า Dark Scrum ซึ่งทำลายแรงจูงใจและความเป็นเจ้าของงาน (Agency) ของนักพัฒนา Dooley & Kazakova (2024) เปรียบเทียบการพัฒนาซอฟต์แวร์ว่าเหมือนการขับรถผ่านภูมิประเทศที่ไม่รู้จัก: ลูกค้าและ Product Owner เป็นผู้กำหนดจุดหมายปลายทาง (Destination) ส่วน Developers คือคนขับรถที่เลือกเส้นทาง (Path) ตามความถนัด สภาพรถ และอุปสรรคตรงหน้า ขณะที่ Project Manager หรือ Scrum Master ต้องไม่ทำตัวเป็น คนสั่งการจากเบาะหลัง (Back-seat driving) หน้าที่ของผู้นำคือติดตามความคืบหน้าและให้ข้อมูลโดยไม่รบกวนสมาธิคนขับ พร้อมจัดสรรเวลาที่ปลอดภัยให้นักพัฒนาได้ลองผิดลองถูกและเรียนรู้จากความผิดพลาด

การจัดการความขัดแย้งและด้านมืดของทีมเวิร์ก (The Dark Side of Teamwork)

  • Social Comfort Zones: การจับคู่หรือปรึกษางานเฉพาะคนที่สนิทหรือมีภูมิหลังเหมือนกัน ทำให้สมาชิกคนอื่นถูกกีดกันออกจากกระบวนการตัดสินใจ
  • Inaccessible Project Information: การคุยประเด็นเทคนิคหรือเปลี่ยนสเปกในแชทส่วนตัว/อีเมลลับ ทำให้ทีมขาดบริบทร่วม ควรใช้ช่องทางเปิดที่ค้นหาได้ (Open Multi-directional Channels)
  • Task Conflicts vs. Personal Conflicts: ความขัดแย้งเชิงงาน (เห็นต่างเรื่องสถาปัตยกรรมหรือวิธีแก้ปัญหา) ช่วยยกระดับคุณภาพผลิตภัณฑ์หากใช้การถกเถียงเชิงสร้างสรรค์ (Constructive Controversy / Rumble ตามแนวคิด Brené Brown) แต่ความขัดแย้งเชิงบุคคล (สไตล์การสื่อสาร อคติ) จะกัดกินพลังงานทีม จึงต้องจัดทำ Team Contract ตั้งแต่เริ่มโครงการและทำ Self & Peer Evaluations เป็นระยะ

2.1 การแปลงความต้องการเป็นงานวิศวกรรม: User Stories (INVEST) และ SMART Tasks

ในแนวทาง Agile ความต้องการของผู้ใช้จะถูกถ่ายทอดในรูปของ User Story ด้วยโครงสร้างมาตรฐาน: As a <role>, I want to <action>, so that <reason/benefit>. เพื่อตอบคำถามว่า ใคร (Who) ต้องการทำ อะไร (What) และ ทำไมถึงเกิดคุณค่า (Why) ตามหลักการ The Three Cs ของ Ron Jeffries (2001) ได้แก่ (1) Card บัตรสรุปความต้องการสั้นๆ, (2) Conversation การสนทนาเจรจาระหว่าง PO, Developer และ QA เพื่อคลี่คลายรายละเอียดและประเมินขนาด, และ (3) Confirmation เกณฑ์การยอมรับ (Acceptance Criteria) ที่แปลงเป็น Automated Acceptance Tests ได้

เพื่อคัดกรองคุณภาพของ User Story ก่อนนำเข้าสู่การพัฒนา Bill Wake ได้เสนอหลักการ INVEST และเมื่อทีมพัฒนาแตก User Story ออกเป็นงานย่อยระดับเทคนิค (Implementation Tasks) ใน Sprint Planning งานย่อยแต่ละชิ้นต้องเป็นไปตามหลัก SMART โดยใช้เวลาทำไม่เกิน 4–16 ชั่วโมง (Sommerville Ch. 23) หรือแนะนำไม่เกิน 1 วัน / ≤ 8 ชั่วโมงทำงาน (Dooley & Kazakova Ch. 4) เพื่อให้ประเมินเวลาได้แม่นยำและเสร็จภายในหนึ่งช่วงการทำงานโดยไม่เกิด Task Switching:

INVEST Criteria สำหรับประเมิน User Story
I — Independent เป็นอิสระต่อกันมากที่สุด สามารถหยิบไปพัฒนาและทดสอบแยกได้เหมือนตัดเค้กหนึ่งชิ้น (Loose Coupling)
N — Negotiable เป็นจุดตั้งต้นการเจรจารายละเอียดทางเทคนิคระหว่าง PO กับทีม ไม่ใช่สัญญาข้อกำหนดที่แข็งทื่อ
V — Valuable ต้องส่งมอบคุณค่าที่จับต้องได้แก่ผู้ใช้หรือลูกค้าจริง แม้ต้องแตก Story ใหญ่ก็ต้องแบ่งตามคุณค่าไม่ใช่แบ่งตามชั้นเทคโนโลยี
E — Estimable ทีมสามารถประเมินความพยายาม (Story Points / Hours) เพื่อจัดลำดับความสำคัญได้ หากประเมินไม่ได้แสดงว่า Story คลุมเครือหรือใหญ่เกินไป
S — Small ขนาดเล็กพอที่จะพัฒนา ทดสอบ และจบได้ภายในหนึ่ง Sprint เพื่อลดภาระการประเมินซ้ำ
T — Testable เขียน Acceptance Criteria และ Unit/Acceptance Tests เพื่อยืนยันความถูกต้องได้ชัดเจน (เชื่อมโยงสู่ Traceability)
SMART Criteria สำหรับแตก Implementation Tasks
S — Specific ระบุรายละเอียดเชิงเทคนิคชัดเจน เช่น โครงสร้างข้อมูล, Endpoint หรือ Component UI ที่ต้องสร้าง การแตก Task มักช่วยเผยให้เห็นข้อกำหนดที่ซ่อนอยู่
M — Measurable วัดความสำเร็จตาม Definition of Done (DoD) เช่น ฟีเจอร์ทำงานครบ Unit Tests ผ่านทั้งหมด และผ่าน Code Review แล้ว
A — Achievable ทำได้จริงภายในขอบเขต Sprint ด้วยทักษะของทีม (หรือเรียนรู้เสริมผ่าน Pair Programming)
R — Relevant ทุก Task ต้องผลักดันให้ User Story ต้นทางเข้าใกล้ความสมบูรณ์และสร้างคุณค่าต่อ Sprint Goal
T — Time-boxed กำหนดเวลาแล้วเสร็จชัดเจน (≤ 8 ชม. หรือ 4–16 ชม.) หากประเมินแล้วใหญ่กว่านี้ให้แบ่งย่อยเป็นหลาย Task และรวมคะแนนให้พอดีกับ Team Velocity

2.2 การจัดการข้อบกพร่องและวงจรชีวิตของ Defect (Defect Management & Lifecycle)

ในระบบวิศวกรรมซอฟต์แวร์ที่เติบโตขึ้น ข้อบกพร่อง (Defects) และคำขอเปลี่ยนแปลง (Change Requests) ต้องถูกบันทึกและควบคุมอย่างเป็นระบบผ่าน Defect Tracking System (เช่น GitHub Issues, Jira, Bugzilla, YouTrack) ในกระบวนการแบบ Plan-driven จะมีเอกสาร Change Request Form (CRF) ส่งให้คณะกรรมการ Change Control Board (CCB) พิจารณาอนุมัติ (Sommerville Ch. 25) ขณะที่ในกระบวนการ Agile ทีมพัฒนาและ PO จะควบคุมรายการผ่าน Product Backlog เพื่อป้องกันการแทรกงานใหม่เข้ากลาง Sprint โดยไม่เข้าใจผลกระทบด้านเวลา (Dooley & Kazakova Ch. 3)

ตามแบบจำลองใน Dooley & Kazakova (2024, บทที่ 19) ทุก Defect ต้องถูกจำแนกความรุนแรง (Defect Severity Levels) 5 ระดับ และเคลื่อนที่ผ่านสถานะมาตรฐานตั้งแต่เริ่มต้นจนปิดงาน (Defect Lifecycle):

ระดับความรุนแรง (Severity) Fagan Classification คำอธิบายและอาการ นโยบายการปล่อยซอฟต์แวร์ (Release Policy)
1. Fatal Major Defect โปรแกรมล่ม (Crash) สูญเสียข้อมูล หรือระบบหยุดทำงานทั้งหมด ห้าม Release เด็ดขาด ต้องแก้ไขเป็นลำดับแรกสุด
2. Severe Major Defect ฟังก์ชันหลักของระบบพัง ใช้งานไม่ได้ และไม่มีวิธีเลี่ยง ห้าม Release เด็ดขาด ไม่อนุญาตให้ส่งมอบถึงผู้ใช้
3. Serious Major Defect ฟังก์ชันทำงานผิดพลาด แต่ยังมีทางเลี่ยง (Workaround) ให้ใช้งานต่อได้ ไม่ควร Release หากยังทราบว่ามีบั๊กระดับ 1–3 ค้างอยู่
4. Trivial Minor Defect จุดบกพร่องเล็กน้อยที่ไม่ทำให้ระบบล่ม เช่น คำสะกดผิด หรือระยะขอบ UI คลาดเคลื่อน อนุญาตให้เลื่อนไปแก้ในรอบถัดไปได้ (Postpone to Backlog)
5. Feature Request Enhancement ไม่ใช่ข้อบกพร่อง แต่เป็นข้อเสนอเพิ่มความสามารถใหม่ในอนาคต ส่งเข้า Product Backlog เพื่อจัดลำดับความสำคัญโดย PO

2.3 การบริหารงานแบบเห็นภาพ: Product Backlog vs. Sprint Backlog และ Kanban WIP Limits

เครื่องมือบริหารโครงการอย่าง GitHub Projects และ Jira ผสานการทำงานของกระดาน Scrum และ Kanban เข้าด้วยกัน โดยมีข้อแตกต่างเชิงวินัยที่ทีม Software House ต้องแยกให้ขาด:

  • Product Backlog vs. Sprint Backlog: Product Backlog คือรายการงานทั้งหมดของโครงการที่ PO ปรับปรุงและจัดลำดับอยู่เสมอ ส่วน Sprint Backlog คือชุดงานที่ทีมพัฒนาเลือกมารับผิดชอบในรอบ Sprint ปัจจุบัน (2–4 สัปดาห์) กฎเหล็กของ Scrum คือ เมื่อ Sprint เริ่มต้นแล้ว ห้ามบุคคลภายนอกเพิ่มงานเข้า Sprint Backlog โดยเด็ดขาด มีเพียง Development Team เท่านั้นที่เพิ่ม Sub-tasks หรือ Bug ที่พบระหว่างทดสอบได้ งานใหม่จากภายนอกต้องไปรอใน Product Backlog เพื่อปกป้อง Sprint Goal (Dooley & Kazakova Ch. 2; Sommerville Ch. 3)
  • Kanban Swimlanes & Pull System: ต่างจาก Scrum ที่มีรอบเวลาตายตัว Kanban เน้นการไหลของงานอย่างต่อเนื่อง (Continuous Flow) โดยใช้ Swimlanes (เส้นแบ่งแนวนอน) แยกประเภทงาน เช่น Bug เร่งด่วน, ฟีเจอร์ใหม่, หรืองานแต่ละทีมย่อย ระบบทำงานแบบ Pull System คือวิศวกรจะดึงงานจากคอลัมน์ก่อนหน้าเข้ามาทำเฉพาะเมื่อตนมีกำลังว่างเท่านั้น
  • Work-In-Progress (WIP) Limits: คือเพดานจำนวนงานสูงสุดที่อนุญาตให้อยู่ในแต่ละคอลัมน์พร้อมกัน (แนะนำ 1–2 งานต่อคน) หากคอลัมน์ Review/QA เต็มเพดาน WIP Limit นักพัฒนาที่เขียนโค้ดเสร็จจะไม่สามารถดันงานใหม่เข้า Review และห้ามดึงงานใหม่เข้า In Progress แต่ต้องกระโดดเข้าไปช่วย Review งานที่ค้างอยู่ การจำกัด WIP เช่นนี้ช่วยเปิดโปงคอขวด (Bottlenecks) ทันที ลดการสลับบริบท (Context Switching) และทำให้ Lead Time (เวลาตั้งแต่ ToDo จนถึง Done) สั้นลงอย่างมีนัยสำคัญ

3.1 ระบบควบคุมเวอร์ชันแบบกระจายศูนย์ (DVCS) เทียบกับระบบรวมศูนย์ (Centralized VCS)

ในบทที่ 25 ของ Sommerville (2016) ได้เปรียบเทียบวิวัฒนาการของระบบจัดการเวอร์ชันจากยุค Centralized Version Control Systems (เช่น Subversion / SVN, CVS) มาสู่ Distributed Version Control Systems (DVCS) เช่น Git และ Mercurial ซึ่งกลายเป็นมาตรฐานอุตสาหกรรมและโครงการ Open-Source ทั่วโลก

มิติเปรียบเทียบ Centralized VCS (เช่น Subversion) Distributed VCS (เช่น Git)
สถาปัตยกรรม Repository มี Master Repository ศูนย์กลางเพียงแห่งเดียว เครื่องนักพัฒนามีเพียง Working Copy ของเวอร์ชันล่าสุด นักพัฒนาทุกคน Clone Local Repository ที่มีประวัติการแก้ไขและ Metadata ครบถ้วนสมบูรณ์ แล้วซิงค์กับ Remote Master Repository
การจัดเก็บข้อมูล นิยมเก็บแบบ Deltas (บันทึกความแตกต่างทีละบรรทัดย้อนหลังไปยังเวอร์ชันตั้งต้น) Git เก็บ Snapshot ของโครงสร้างโปรเจกต์และอ้างอิงผ่าน Object Checksums (SHA-1/SHA-256 Hash) ทำให้ตรวจสอบความถูกต้อง (Integrity) และสลับ Branch ได้รวดเร็ว
การทำงาน Offline & ความทนทาน ต้องเชื่อมต่อเซิร์ฟเวอร์กลางจึงจะ Commit หรือดูประวัติได้ หากเซิร์ฟเวอร์ล่มทีมทำงานต่อไม่ได้ Commit, สร้าง Branch และดูประวัติบน Local Repo ได้แบบ Offline เต็มรูปแบบ และ Local Repo ของทุกคนทำหน้าที่เป็น Backup ของระบบ
การรองรับการทดลอง (Branching) การสร้าง Branch และ Merge ทำได้ช้าและซับซ้อน Branch เป็นเพียง Pointer ขนาดเล็ก (41 bytes) ชี้ไปยัง Commit Checksum ทำให้สร้างและ Merge Branch ได้ในเสี้ยววินาที

3.2 แบบจำลองการแก้ปัญหาการแก้ไขไฟล์ชนกัน (Collision Resolution Models)

เมื่อวิศวกรหลายคนใน Software House แก้ไขซอร์สโค้ดชุดเดียวกันพร้อมกัน ระบบควบคุมเวอร์ชันมี 2 แนวทางหลักในการจัดการการชนกัน (Sommerville Ch. 25):

PESSIMISTIC MODEL

Lock-Modify-Unlock

นักพัฒนาต้องขอ Check-out พร้อมล็อกไฟล์ จากเซิร์ฟเวอร์ก่อนแก้ไข ระหว่างนั้นคนอื่นอ่านได้อย่างเดียวจนกว่าเจ้าของจะ Commit และปลดล็อก ข้อดีคือไม่มีวันเกิด Merge Conflict แต่ข้อเสียร้ายแรงคือทำให้เกิดคอขวด หากคนถือล็อกลืมปลดล็อกหรือแก้ไฟล์ศูนย์กลางร่วมกัน ทีมที่เหลือทั้งหมดจะหยุดชะงัก

OPTIMISTIC MODEL (GIT STANDARD)

Copy-Modify-Merge

ทุกคนแก้ไขสำเนาไฟล์พร้อมกันได้อย่างอิสระ เมื่อนำงานมารวมกัน หากแก้ไขคนละไฟล์หรือคนละช่วงบรรทัด ระบบจะทำ Automatic Merge ให้โดยอัตโนมัติ แต่หากแก้ไขบรรทัดเดียวกัน ระบบจะหยุดและแจ้ง Merge Conflict เพื่อให้นักพัฒนาตรวจสอบความหมายเชิงตรรกะและผสานโค้ดด้วยตนเอง (Manual Merge)

1. Code Walkthrough ผู้เขียนโค้ดเป็นผู้อธิบายตรรกะทีละส่วนให้เพื่อนร่วมทีมฟังแบบไม่เป็นทางการเพื่อค้นหาจุดบกพร่องและแลกเปลี่ยนความรู้ เป็นทางการน้อย เหมาะกับทีมขนาดเล็กหรือการ Rework โค้ดที่แก้ไขไม่ถึง 10%
2. Peer Code Review (Pull Request) นักพัฒนาเปิด Pull Request (PR) บน GitHub/GitLab เพื่อขอให้เพื่อนร่วมทีมอย่างน้อย 1–2 คนอ่าน Diff ตรวจสอบ Style, Logic, Edge Cases และ Security แบบ Asynchronous เป็นทางการปานกลาง เป็นมาตรฐานหลักของ Software House และโครงการ Agile ยุคใหม่
3. Fagan Inspection (6 Phases) การตรวจพินิจเชิงวิศวกรรมแบบเข้มงวด 6 ขั้นตอน: Planning → Overview → Preparation → Inspection Meeting (≤ 2 ชม.) → Inspection Report → Rework & Follow-up โดยแยกบทบาท Moderator (คุมการประชุม), Reader (อ่านถอดความโค้ด), Recorder (จดบันทึก Severity & Metrics) และ Author (ห้ามโต้เถียง ตอบคำถามอย่างเดียว และห้ามแก้ปัญหาในห้องประชุม) หากต้องแก้โค้ดเกิน 10% ต้องจัด Inspection ใหม่ เป็นทางการสูงสุด ใช้กับระบบ Safety-critical (เช่น ปั๊มอินซูลิน ระบบการบิน) หรือโมดูลแกนหลักที่มีความเสี่ยงสูง
การตั้งค่า Branch Protection Rules เพื่อบังคับใช้คุณภาพระดับองค์กร

เครื่องมืออย่าง GitHub ช่วยเปลี่ยนกฎเกณฑ์ทางวิศวกรรมให้เป็นกลไกบังคับอัตโนมัติ (Automated Gatekeeping) บน Branch main (และ develop): (1) Require a pull request before merging ห้าม Push ตรงเข้า main เด็ดขาด, (2) Require approvals ต้องมี Peer Review อนุมัติอย่างน้อย 1–2 คนและยกเลิกการอนุมัติอัตโนมัติเมื่อมีการ Push โค้ดใหม่, (3) Require status checks to pass บังคับให้ CI Build และ Unit Tests ผ่าน 100%, และ (4) Require conversation resolution ต้องเคลียร์คอมเมนต์ Review ทั้งหมดก่อนกด Merge

4.1 Continuous Integration (CI) และ Continuous Delivery (CD) (Sommerville Ch. 25)

ปัญหาใหญ่ของการพัฒนาเป็นทีมคือ “Integration Hell” เมื่อนักพัฒนาแยกกันเขียนโค้ดหลายสัปดาห์แล้วนำมารวมกันก่อนวันส่งงาน ทำให้ระบบพังพร้อมกันหลายจุด แนวคิด Continuous Integration (CI) จึงกำหนดให้นักพัฒนาผสานโค้ดเข้าสู่ Mainline บ่อยที่สุด (อย่างน้อยวันละครั้งหรือทุกครั้งที่จบ Task) โดยมี Automated Build Server (เช่น GitHub Actions, Jenkins) ทำงานตามลำดับอัตโนมัติ:

  1. นักพัฒนารันทดสอบบนเครื่องตนเองก่อน Push (Check-before-check-in)
  2. เมื่อ Push หรือเปิด Pull Request ระบบ CI Server จะ Checkout โค้ดเวอร์ชันล่าสุดมาสร้าง Build ใหม่ในสภาพแวดล้อมสะอาด (Clean Environment)
  3. รันชุดทดสอบอัตโนมัติ (Unit Tests, Integration Tests และ Regression Tests เพื่อยืนยันว่าของใหม่ไม่ทำของเดิมพัง)
  4. ยึดกฎเหล็ก “Never Break the Build”: หาก Pipeline ล้มเหลว ทีมต้องหยุดเพิ่มฟีเจอร์ใหม่และรีบแก้ไข Build ให้กลับมาเขียวทันที

ต่อยอดจาก CI คือ Continuous Delivery (CD) ที่รับประกันว่าซอฟต์แวร์ใน Mainline อยู่ในสถานะที่พร้อมนำไป Deploy ขึ้นระบบจริง (Staging/Production) ได้ตลอดเวลาด้วยการกดอนุมัติเพียงครั้งเดียว หรือขยับไปสู่ Continuous Deployment ที่ปล่อยขึ้น Production อัตโนมัติเมื่อผ่านทุก Quality Gates

ตัวอย่าง GitHub Actions CI Workflow (.github/workflows/ci.yml) 
name: Software House CI Gate
on:
  pull_request:
    branches: [ main, develop ]
  push:
    branches: [ main ]

jobs:
  build-and-test:
    runs-on: ubuntu-latest
    steps:
      - name: Checkout repository
        uses: actions/checkout@v4
      - name: Setup Node.js Runtime
        uses: actions/setup-node@v4
        with:
          node-version: '20'
          cache: 'npm'
      - name: Install dependencies cleanly
        run: npm ci
      - name: Run Static Linter & Type Check
        run: npm run lint
      - name: Execute Unit & Regression Tests
        run: npm test -- --coverage

4.2 ตัววัดกระบวนการพัฒนาและคุณภาพซอฟต์แวร์ (Software Process & Quality Metrics)

Sommerville (2016, บทที่ 24: Quality Management) ระบุว่าการบริหารคุณภาพที่ดีต้องอาศัยการวัดผลเชิงปริมาณ (Software Measurement) ทั้ง Process Metrics (ใช้วัดความเร็วและความเสถียรของกระบวนการ) และ Product Metrics (ใช้วัดความซับซ้อนและข้อบกพร่องภายในตัวซอฟต์แวร์) เพื่อใช้ควบคุมโครงการและพยากรณ์ปัญหาล่วงหน้า:

AGILE CAPACITY

Velocity

ปริมาณงาน (Story Points) ที่ทีมทำเสร็จสมบูรณ์ตาม Definition of Done ใน 1 Sprint ใช้เป็นฐานพยากรณ์กำลังการผลิตใน Sprint ถัดไป (Sommerville Ch. 3, 23) ห้ามนำ Velocity ข้ามทีมมาเปรียบเทียบแข่งขันกันเพราะสเกลคะแนนแต่ละทีมต่างกัน

FLOW EFFICIENCY

Lead Time vs. Cycle Time

Lead Time วัดตั้งแต่ Task ถูกสร้างเข้า ToDo จนถึง Done (มุมมองลูกค้า) ส่วน Cycle Time วัดตั้งแต่ทีมเริ่มลงมือทำจริง (In Progress) จนถึง Done (มุมมองประสิทธิภาพวิศวกรรม) การลด WIP Limit ช่วยลด Cycle Time โดยตรง

SPRINT TRACKING

Burn-down & Burn-up Charts

Burn-down แสดงปริมาณงานที่เหลือเทียบกับเส้นอุดมคติรายวัน; Burn-up แยกเส้น “งานที่เสร็จสะสม” ออกจากเส้น “ขอบเขตงานรวม (Total Scope)” ทำให้เห็นชัดทันทีหากความล่าช้าเกิดจาก Scope Creep

BOTTLENECK RADAR

Cumulative Flow Diagram (CFD)

กราฟพื้นที่ซ้อนทับแสดงจำนวน Ticket ในทุกคอลัมน์ตามเวลา หากแถบสีของสถานะ In Review พองตัวหนาขึ้นเรื่อยๆ แปลว่าเกิดคอขวดในขั้นตอน Code Review หรือ QA ต้องรีบปรับสมดุลทีม

RELIABILITY QUALITY

Defect Density

อัตราส่วนจำนวนข้อบกพร่องที่พบต่อขนาดซอฟต์แวร์ (เช่น Defects / KLOC หรือ Defects / Story Point) ใช้ประเมินความน่าเชื่อถือของโมดูลและระบุไฟล์ที่เป็นจุดเสี่ยง (Bug Hotspots) เพื่อส่งไป Refactor

STRUCTURAL COMPLEXITY

Fan-in / Fan-out & Cyclomatic Complexity

Fan-in สูงแปลว่าโมดูลถูกเรียกใช้มาก (แก้กระทบกว้าง) Fan-out สูงแปลว่าโมดูลพึ่งพาผู้อื่นมาก (ซับซ้อน/เปราะบาง) ส่วน Cyclomatic Complexity V(G) = E - N + 2 (Sommerville Ch. 24) วัดจำนวนเส้นทางตรรกะอิสระและกำหนดจำนวน Test Cases ขั้นต่ำที่ต้องเขียน

4.3 ระบบ Build อัตโนมัติและการจัดการการปล่อยเวอร์ชัน (System Building & Release Management)

Sommerville (2016, บทที่ 7 & 25) อธิบายว่าการสร้างระบบ (System Building) คือกระบวนการคอมไพล์และเชื่อมโยงไฟล์ซอร์สโค้ด ไลบรารีภายนอก และไฟล์ตั้งค่าให้เป็น Executable System โดยอาศัยองค์ประกอบสำคัญ 3 ประการ:

  • Baselines & Semantic Tagging: เมื่อซอฟต์แวร์ผ่านการทดสอบระบบ (System Testing) แล้ว ทีมจะแช่แข็งเวอร์ชันขององค์ประกอบทั้งหมดเป็น Baseline และติดป้ายกำกับด้วย Git Tag ตามมาตรฐาน Semantic Versioning (vMAJOR.MINOR.PATCH เช่น v1.2.0) เพื่อให้สามารถย้อนกลับมาสร้างซอฟต์แวร์เวอร์ชันเดิมซ้ำได้ทุกเมื่อ (Reproducible Build)
  • Release Notes: เอกสารสรุปการเปลี่ยนแปลงสำหรับผู้ใช้และทีมสนับสนุน ระบุฟีเจอร์ใหม่ บั๊กที่แก้ไข ข้อจำกัดที่ยังทราบ (Known Issues) และวิธีอัปเกรด ซึ่งเครื่องมือสมัยใหม่สามารถสร้างอัตโนมัติจาก Merged Pull Requests และ Conventional Commits
  • Host-Target Development Platforms: การพัฒนาซอฟต์แวร์มักเกิดขึ้นบนเครื่อง Host (แล็ปท็อปนักพัฒนาหรือ Cloud CI Runner) ซึ่งมีสถาปัตยกรรม CPU หรือระบบปฏิบัติการต่างจากเครื่อง Target (เช่น Embedded Hardware อย่างเครื่องปั๊มอินซูลิน, สถานีอากาศ, มือถือ หรือ Docker Container บน Production Server) การใช้ Cross-compilers, Containerization (Docker) และ Hardware Emulators ใน CI จึงสำคัญอย่างยิ่งเพื่อรับประกันว่าโค้ดที่รันผ่านบนเครื่องนักพัฒนาจะทำงานบนเครื่องเป้าหมายได้จริง

Labels: type:story, priority:P1, module:auth
Milestone: Sprint 1 - Core MVP

### User Story
As an **Undergraduate Student**,
I want to **sign in with my university email and password**,
so that **I can access my team's project workspace securely**.

### Acceptance Criteria (Confirmation)
- [ ] อีเมลที่ไม่ได้ลงท้ายด้วยโดเมนมหาวิทยาลัยต้องถูกปฏิเสธด้วย HTTP 400
- [ ] รหัสผ่านต้องถูก Hash ด้วย bcrypt ก่อนบันทึกลงฐานข้อมูล
- [ ] Login สำเร็จต้องคืนค่า JWT Token ที่มีอายุ 24 ชั่วโมง

### SMART Implementation Tasks (≤ 8 hrs each)
- [ ] Task 1.1: ออกแบบ Schema ตาราง users และ Migration script (3 hrs)
- [ ] Task 1.2: พัฒนา POST /api/auth/login + Validation (4 hrs)
- [ ] Task 1.3: เขียน Unit Tests ครอบคลุม Valid/Invalid cases (3 hrs)

Simulating a Feature Sprint (Branch → Code → PR → Review → CI → Merge)

ให้นักพัฒนาในกลุ่มจับคู่ (หรือทำคนละ 1 Issue) จำลองวงจรการทำงานจริงครบ Loop ตั้งแต่ต้นจนจบ: แตก Branch จาก main, เขียนโค้ดพร้อม Unit Test, Commit ด้วยข้อความสื่อความหมาย, Push ขึ้น Remote, เปิด Pull Request พร้อมเชื่อม Closes #1, ให้เพื่อนร่วมทีมทำ Peer Code Review อย่างน้อย 2 ความเห็นเชิงสร้างสรรค์, รอให้ GitHub Actions CI ขึ้นเครื่องหมายถูกสีเขียว แล้วจึงกด Merge และลบบ้านเดิม (Delete Feature Branch)

Feature Sprint CLI Simulation Script 
# 1. อัปเดต main ให้ล่าสุดก่อนแตก Branch เสมอ
git checkout main
git pull origin main

# 2. แตก Feature Branch ตามชื่อ Issue
git checkout -b feature/us01-student-login

# 3. เขียนโค้ด + รันทดสอบบนเครื่องตนเอง (Check-before-check-in)
npm test

# 4. Stage และ Commit ตามมาตรฐาน Conventional Commits
git add src/auth.js tests/auth.test.js
git commit -m "feat(auth): implement university email login validation (#1)"

# 5. Push ขึ้น Remote Repository และเปิด Pull Request
git push -u origin feature/us01-student-login
gh pr create --base main --title "feat(auth): Student Login (#1)" --body "Closes #1"

# 6. หลังผ่าน Peer Code Review + GitHub Actions CI สีเขียว -> Merge & Cleanup
gh pr merge --squash --delete-branch

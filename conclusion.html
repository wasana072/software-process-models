MODULE 01

Foundations of Software Engineering & SDLC — รากฐานวิศวกรรมซอฟต์แวร์และวงจรชีวิตการพัฒนา

ปูพื้นฐานความเข้าใจว่าเหตุใดการพัฒนาซอฟต์แวร์ระดับอาชีพจึงต้องอาศัยกระบวนการที่เป็นระบบ ศึกษาตัวแปรข้อจำกัดของโครงการ คุณลักษณะคุณภาพซอฟต์แวร์ ความแตกต่างระหว่าง Verification กับ Validation และหลักการเลือกใช้โมเดลตามบริบทของระบบ

1.1 นิยามและความสำคัญของ Software Process และ Software Process Modeling

ในมุมมองของบุคคลทั่วไป ซอฟต์แวร์อาจหมายถึงเพียงโปรแกรมคอมพิวเตอร์หรือซอร์สโค้ด แต่ตามนิยามของ Ian Sommerville (2016) ซอฟต์แวร์ระดับอาชีพ (Professional Software) ไม่ได้มีเพียงโปรแกรมที่รันได้เท่านั้น หากแต่ครอบคลุมถึง ไลบรารี ไฟล์ตั้งค่าระบบ (Configuration Data) เอกสารระบบ (System Documentation) คู่มือผู้ใช้ (User Documentation) รวมถึงเว็บไซต์สนับสนุน เพื่อให้บุคคลอื่นสามารถใช้งาน บำรุงรักษา และพัฒนาต่อยอดได้ตลอดอายุขัยของระบบ

ผลิตภัณฑ์ซอฟต์แวร์แบ่งออกเป็น 2 ประเภทหลักที่มีผลโดยตรงต่อการบริหารความต้องการและกระบวนการพัฒนา ได้แก่

Generic Products (ซอฟต์แวร์สำเร็จรูป)

Market-Driven

ระบบที่องค์กรพัฒนาขึ้นเพื่อจำหน่ายในตลาดเสรีแก่ลูกค้าทั่วไป เช่น แอปพลิเคชันมือถือ ฐานข้อมูล โปรแกรมสำนักงาน หรือระบบเฉพาะทาง (Vertical Applications) จุดสำคัญคือ ผู้พัฒนาเป็นผู้ควบคุม Specification เอง จึงปรับขอบเขตได้เมื่อเกิดอุปสรรค

Customized / Bespoke Software (ซอฟต์แวร์สั่งทำ)

Contract-Driven

ระบบที่พัฒนาตามการว่าจ้างของลูกค้ารายใดรายหนึ่งโดยเฉพาะ เช่น ระบบควบคุมอุปกรณ์การแพทย์ ระบบควบคุมจราจรทางอากาศ หรือระบบกระบวนการธุรกิจเฉพาะองค์กร จุดสำคัญคือ ผู้ซื้อหรือลูกค้าเป็นผู้ควบคุม Specification ทีมพัฒนาต้องส่งมอบให้ตรงตามข้อตกลง

อย่างไรก็ตาม ปัจจุบันเส้นแบ่งระหว่างสองประเภทเริ่มเลือนรางลง ระบบธุรกิจจำนวนมากใช้แนวทางนำ Generic Product เช่น ERP (SAP, Oracle) มาเป็นฐานแล้วปรับแต่ง (Customize) กฎทางธุรกิจและรายงานเพิ่มเติมให้เข้ากับองค์กร

Software Process (กระบวนการซอฟต์แวร์) คือ ลำดับของกิจกรรมที่เชื่อมโยงกันเพื่อนำไปสู่การผลิตและวิวัฒนาการของผลิตภัณฑ์ซอฟต์แวร์ แม้แต่ละองค์กรจะมีกระบวนการที่แตกต่างกัน แต่ทุกกระบวนการต้องประกอบด้วย 4 กิจกรรมพื้นฐาน (Fundamental Process Activities) ได้แก่

  1. Software Specification (การกำหนดคุณลักษณะ): ลูกค้าและวิศวกรร่วมกันนิยามฟังก์ชันที่ระบบต้องทำและข้อจำกัดในการทำงาน
  2. Software Development (การพัฒนาซอฟต์แวร์): การออกแบบสถาปัตยกรรม ออกแบบรายละเอียด และการเขียนโปรแกรมให้เป็นไปตามข้อกำหนด
  3. Software Validation (การตรวจสอบความถูกต้อง): การตรวจเช็คและทดสอบว่าระบบทำงานตรงตามข้อกำหนดและตอบโจทย์ความต้องการจริงของผู้ใช้
  4. Software Evolution (การวิวัฒนาการซอฟต์แวร์): การปรับปรุงและเปลี่ยนแปลงซอฟต์แวร์หลังส่งมอบเพื่อให้สอดรับกับความต้องการทางธุรกิจและเทคโนโลยีที่เปลี่ยนไป

Software Process Modeling คือ การสร้างแบบจำลองเชิงนามธรรม (Simplified Representation) ของกระบวนการพัฒนาซอฟต์แวร์ เพื่อใช้สื่อสาร กำหนดมาตรฐาน ฝึกอบรม และปรับปรุงวิธีการทำงานในทีม แบบจำลองหนึ่งๆ มักแสดงมุมมองเฉพาะด้าน เช่น มุมมองลำดับกิจกรรม (Workflow), มุมมองการไหลของข้อมูลและเอกสาร (Data-flow / Artifacts), และ มุมมองบทบาทหน้าที่ของผู้เกี่ยวข้อง (Role / Action)

1.2 Triple Constraint (3+3 Variables) และ Engineering Paradox

ตามกรอบความรู้ของ Project Management Institute (PMI) และตำราของ Dooley & Kazakova (2024) การพัฒนาซอฟต์แวร์อยู่ภายใต้แรงกดดันของตัวแปรหลัก 3 ประการที่เรียกว่า Iron Triangle (Triple Constraint) ได้แก่ Cost (งบประมาณ/ทรัพยากร), Time (กำหนดเวลา) และ Scope (ขอบเขตฟังก์ชันงาน) โดยมี Quality (คุณภาพ) อยู่ตรงจุดศูนย์กลาง การกำหนดค่าของสองตัวแปรย่อมบังคับให้ตัวแปรที่สามต้องปรับตัวตาม เช่น หากลูกค้าล็อกงบประมาณและกำหนดวันส่งมอบตายตัว ทีมวิศวกรจำเป็นต้องบริหารจัดการ Scope อย่างเคร่งครัดเพื่อไม่ให้คุณภาพพังทลาย

ในโครงการยุคใหม่ โมเดล 3 ตัวแปรได้ถูกขยายเป็น 6 Variables of Software Development (Siegelaub, 2007) โดยเพิ่ม Quality, Risk (ความเสี่ยง) และ Benefits (คุณค่าทางธุรกิจที่ได้รับ) เข้ามาพิจารณาร่วมกัน การลดระยะเวลาส่งมอบโดยไม่ลด Scope และไม่เพิ่มคน มักนำไปสู่การแอบลด Quality หรือการสะสม Technical Debt ซึ่งต้องจ่ายคืนด้วยต้นทุนการแก้ไขที่สูงกว่าเดิมหลายเท่าในรุ่นถัดไป

Engineering Paradox และคุณลักษณะสำคัญของซอฟต์แวร์ที่ดี

Engineering Paradox (ความย้อนแย้งทางวิศวกรรมซอฟต์แวร์) เกิดจากธรรมชาติของซอฟต์แวร์ที่จับต้องไม่ได้ (Intangible) และไร้ข้อจำกัดทางกายภาพหรือกฎหมายการผลิต ทำให้ใครๆ ก็เขียนโปรแกรมที่ "ดูเหมือนทำงานได้" โดยไม่ใช้กระบวนการวิศวกรรมได้ง่าย แต่เมื่อระบบขยายขนาดขึ้น ความซับซ้อนจะทวีคูณจนควบคุมไม่ได้ นอกจากนี้ ยิ่งเทคโนโลยีวิศวกรรมซอฟต์แวร์ก้าวหน้าและช่วยให้สร้างระบบใหญ่ขึ้นได้เร็วเท่าไร ความคาดหวังของตลาดและผู้ใช้งานก็ยิ่งเรียกร้องระบบที่ซับซ้อนยิ่งขึ้นและเร็วขึ้นกว่าเดิมเสมอ (Sommerville, 2016)

ในเชิงเศรษฐศาสตร์ซอฟต์แวร์ โดยเฉลี่ย 60% ของต้นทุนการพัฒนาอยู่ที่การออกแบบและเขียนโปรแกรม และอีก 40% อยู่ที่การทดสอบ แต่สำหรับ Custom Software ตลอดอายุการใช้งาน ค่าใช้จ่ายในการวิวัฒนาการและบำรุงรักษา (Evolution/Maintenance Costs) มักสูงกว่าค่าพัฒนาเริ่มต้น ดังนั้น ซอฟต์แวร์ระดับอาชีพจึงต้องมีคุณลักษณะคุณภาพหลัก 4 ประการ (Sommerville Fig. 1.2)

คุณลักษณะ (Attribute) คำอธิบายเชิงวิศวกรรม ตัวอย่างรูปธรรมตามประเภทระบบ
1. Acceptability
การยอมรับของผู้ใช้		 ระบบต้องเข้าใจง่าย ใช้งานได้สะดวก (Usable) และทำงานร่วมกับระบบเดิมที่ผู้ใช้มีอยู่ได้อย่างราบรื่น ระบบ Mentcare ต้องใช้งานง่ายสำหรับแพทย์และพยาบาลในคลินิกชุมชนที่มีภาระงานสูง
2. Dependability & Security
ความเชื่อถือได้และความปลอดภัย		 ครอบคลุม Reliability, Safety และ Security ระบบต้องไม่ก่อความเสียหายต่อชีวิตหรือทรัพย์สิน และป้องกันการเข้าถึงโดยมิชอบ ระบบ Insulin Pump ต้องจ่ายอินซูลินแม่นยำ 100% และไม่หยุดทำงานในภาวะวิกฤต
3. Efficiency
ประสิทธิภาพการใช้ทรัพยากร		 ไม่ใช้หน่วยความจำ รอบซีพียู หรือพลังงานแบตเตอรี่อย่างสิ้นเปลือง รวมถึงเวลาตอบสนอง (Responsiveness) ที่เหมาะสม Wilderness Weather Station ต้องบริหารพลังงานแบตเตอรี่จากโซลาร์เซลล์และส่งข้อมูลผ่านดาวเทียมแบนด์วิดท์ต่ำ
4. Maintainability
ความสามารถในการบำรุงรักษา		 โครงสร้างโค้ดและเอกสารต้องออกแบบให้วิศวกรคนอื่นเข้ามาแก้ไข เพิ่มฟีเจอร์ และปรับเปลี่ยนตามสภาพแวดล้อมได้ง่าย ระบบ iLearn ที่โรงเรียนต้องปรับเปลี่ยนเครื่องมือการเรียนรู้และเชื่อมต่อบริการภายนอกใหม่ๆ ได้เสมอ

1.3 วงจรชีวิตการพัฒนาซอฟต์แวร์ (SDLC Core Phases) และการเปรียบเทียบ Verification vs. Validation

Software Development Lifecycle (SDLC) คือ ลำดับช่วงชีวิตของซอฟต์แวร์ตั้งแต่ถือกำเนิดจนปลดระวาง Dooley & Kazakova (2024) สรุปขั้นตอนแกนหลักของ SDLC ไว้ครบถ้วน 8 ขั้นตอน (โดยขั้นตอนหลักที่ดำเนินการซ้ำในทุกโครงการมี 5–6 ขั้นตอนแรก):

1. Conception & Feasibility

Phase 01

การระบุปัญหาทางธุรกิจ การศึกษาความเป็นไปได้ทางเทคนิค เศรษฐศาสตร์ และกฎหมาย รวมถึงการกำหนดวิสัยทัศน์เบื้องต้น

2. Requirements & Modeling

Phase 02

การรวบรวม วิเคราะห์ จัดทำข้อกำหนดความต้องการ (Functional & Non-functional) และสร้างแบบจำลองระบบ

3. System & Software Design

Phase 03

การวางสถาปัตยกรรมระบบ (Architecture) โครงสร้างฐานข้อมูล อินเทอร์เฟซ และการออกแบบรายละเอียดระดับโมดูล/คลาส

4. Coding & Debugging

Phase 04

การแปลงแบบจำลองการออกแบบให้เป็นซอร์สโค้ดที่ทำงานได้ การทดสอบระดับหน่วย (Unit Test) และการแก้ไขจุดบกพร่องเบื้องต้น

5. Integration & Testing

Phase 05

การรวมส่วนประกอบย่อยเข้าด้วยกัน (Integration Testing) การทดสอบทั้งระบบ (System Testing) และการทดสอบยอมรับโดยผู้ใช้ (UAT)

6. Release, Evolution & Retirement

Phase 06–08

การติดตั้งใช้งานจริง (Deployment) การบำรุงรักษาและพัฒนาต่อเนื่อง (Maintenance/Evolution — ยาวนานที่สุด) จนถึงการปลดระวางระบบ

Verification vs. Validation (V&V) — ความแตกต่างที่นักวิศวกรซอฟต์แวร์ต้องไม่สับสน

Barry Boehm (1979) นิยามความแตกต่างของ V&V ไว้อย่างคมชัด และถูกเน้นย้ำใน Sommerville บทที่ 8 ดังนี้:

  • Verification ("Are we building the product right?"): การตรวจสอบว่าซอฟต์แวร์ถูกสร้างขึ้นสอดคล้องกับ Specification ที่ระบุไว้ ทั้งในเชิงฟังก์ชันและ Non-functional หรือไม่ (เช่น โค้ดคำนวณภาษีตรงตามสูตรในเอกสาร Spec หรือไม่)
  • Validation ("Are we building the right product?"): การตรวจสอบว่าซอฟต์แวร์ที่สร้างขึ้นตอบสนอง ความต้องการและบริบทการใช้งานจริงของลูกค้า หรือไม่ (แม้ระบบจะทำตาม Spec 100% แต่หาก Spec ต้นทางเข้าใจผู้ใช้ผิด Validation ก็จะไม่ผ่าน)

Edsger Dijkstra (1972) เตือนไว้ว่า "Testing can only show the presence of errors, not their absence" ดังนั้นกระบวนการ V&V ที่สมบูรณ์จึงต้องผสานทั้ง Static V&V (การตรวจโดยไม่รันโค้ด เช่น Requirements Review, Code Inspection, Static Analysis, Model Checking) และ Dynamic V&V (การรันโปรแกรมทดสอบทั้ง Defect Testing เพื่อหาบั๊ก และ Validation Testing เพื่อยืนยันการทำงานตามปกติ)

1.4 ผลลัพธ์เชิงรูปธรรมในแต่ละเฟส (Software Process Artifacts Matrix)

ทุกเฟสของ SDLC ต้องผลิตชิ้นงานหรือผลลัพธ์เชิงรูปธรรม (Artifacts) เพื่อส่งต่อองค์ความรู้ ลดการตีความผิดพลาด และใช้เป็นเกณฑ์ผ่านด่าน (Gate Criteria) ในการประเมินความก้าวหน้า ตารางต่อไปนี้สรุป Artifacts สำคัญตั้งแต่ต้นจนจบวงจรชีวิต

เฟส SDLC กิจกรรมหลัก ผลลัพธ์เชิงรูปธรรม (Artifacts) ผู้รับผิดชอบหลัก เกณฑ์ยืนยันคุณภาพ (Exit Criteria)
1. Conception ประเมินปัญหาและความคุ้มค่า Project Charter, Feasibility Report, Business Case, High-level Risk Log Stakeholders, PM, Product Owner อนุมัติงบประมาณ ขอบเขตเบื้องต้น และความเป็นไปได้
2. Requirements Elicitation, Analysis & Spec SRS (Software Requirements Spec), Use Case / User Stories, Domain Model, Wireframes BA, Product Owner, System Analyst ผ่าน Requirements Validation (Validity, Consistency, Completeness, Realism, Verifiability)
3. Design Architectural & Detailed Design Architecture Document (SDD), UML Diagrams (Class, Sequence, State), ERD, API Contract (OpenAPI) Software Architect, Tech Lead, UI/UX Design Review ผ่าน, สนับสนุน Non-functional Requirements ได้จริง
4. Implementation Coding, Refactoring & Unit Test Source Code (ใน VCS), Unit Test Suites, Build Scripts, Config Files Developers, Engineers Code Review / PR Approved, Unit Tests Pass, Static Analysis Clean
5. Testing (V&V) Integration, System & User Testing Test Plan, Test Cases, Defect/Bug Reports, Automated Regression Suite, UAT Sign-off QA Engineers, Independent Testers, End-Users Critical Defects = 0, Acceptance Criteria ผ่านครบถ้วน
6. Release & Evolution Deployment, Ops & Maintenance Release Notes, Deployment Package/Docker, User Manual, Monitoring Logs, Change Requests DevOps / SRE, Support, Maintenance Team ระบบเสถียรใน Production, SLA เป็นไปตามเป้าหมาย

1.5 หลักการเลือก Process Model ตามบริบท (Context-Driven Selection) และแนวคิด "No Silver Bullet"

ในบทความคลาสสิก "No Silver Bullet — Essence and Accidents of Software Engineering" (1987) ที่อ้างอิงในตำรา Dooley & Kazakova (2024) Frederick Brooks ชี้ให้เห็นว่าความยากของการพัฒนาซอฟต์แวร์แบ่งเป็น 2 ส่วน คือ Accidental Complexity (ความยุ่งยากจากเครื่องมือ ภาษาโปรแกรม หรือฮาร์ดแวร์ ซึ่งพัฒนาดีขึ้นได้มาก) และ Essential Complexity (ความซับซ้อนโดยเนื้อแท้ของปัญหา เช่น ความซับซ้อนของกฎธุรกิจ การเปลี่ยนแปลงของความต้องการ และการสื่อสารระหว่างมนุษย์) ซึ่งไม่มีเทคโนโลยีหรือ Process Model วิเศษใดเพียงหนึ่งเดียวที่สามารถลดความซับซ้อนหลักให้หายไปได้ในชั่วข้ามคืน

สอดคล้องกับหลักการของ Sommerville (2016) ที่ย้ำว่า "ไม่มีกระบวนการซอฟต์แวร์แบบสากลที่เหมาะสมกับทุกระบบ" การเลือกโมเดลต้องอ้างอิงบริบทจริงของโครงการ (Context-Driven Selection — Sommerville Fig. 3.12) โดยพิจารณาจาก: ประเภทของระบบ, ระดับความวิกฤต (Criticality), ความผันผวนของความต้องการ, ขนาดและการกระจายตัวของทีม, ข้อกำหนดทางกฎหมายและสัญญา และ วัฒนธรรมองค์กร

ประเภทระบบ (Sommerville 1.1.2) ลักษณะเด่นและความเสี่ยง Process Model ที่เหมาะสม
Embedded Control Systems ควบคุมฮาร์ดแวร์โดยตรง แก้ไขหลังผลิตยาก (ROM) ต้องมั่นใจเรื่อง Safety Plan-Driven / Waterfall / V-Model + Formal Verification
Interactive Web / Mobile Apps ความต้องการเปลี่ยนไว ต้องการ UX ดีและปล่อยฟีเจอร์แข่งกับตลาดเร็ว Agile (Scrum / XP) + Incremental Delivery + Prototyping
Organizational Information Systems เชื่อมฐานข้อมูลขนาดใหญ่ ต้องปรับใช้ร่วมกับระบบเดิมหรือ ERP Hybrid (Architecture Plan-Driven + Agile Feature Sprints / Integration & Config)
Data Collection & Simulation ทำงานในสภาพแวดล้อมปิด/รุนแรง ประมวลผลสูง หรือวิเคราะห์ Big Data Spiral / Incremental Model เน้น Prototyping อัลกอริทึมและฮาร์ดแวร์
Systems of Systems (SoS) ประกอบด้วยหลายระบบย่อยอิสระจากหลายองค์กร/ทีม (Brownfield) Plan-Driven Interface Contracts + Agile ภายในแต่ละทีมย่อย (Scaled Agile)

MODULE 02

Traditional Software Process Models & Their Limitations — โมเดลกระบวนการแบบดั้งเดิมและข้อจำกัด

เจาะลึกโมเดลแบบวางแผนล่วงหน้า (Plan-Driven) ได้แก่ Waterfall Model และ V-Model วิเคราะห์จุดแข็งในระบบที่ต้องการความแม่นยำและตรวจสอบได้ทางกฎหมาย พร้อมถอดรหัสข้อจำกัดเชิงโครงสร้างที่นำไปสู่ต้นทุนความผิดพลาดมหาศาลในเฟสท้ายของโครงการ

2.1 โครงสร้างและหลักการของ Waterfall Model (Phase Gates & Document-Driven)

Waterfall Model เป็นโมเดลกระบวนการซอฟต์แวร์แบบ Plan-Driven ตัวแรกที่ได้รับการตีพิมพ์อย่างเป็นทางการโดย Winston Royce (1970) โดยดัดแปลงมาจากสายการผลิตทางวิศวกรรมฮาร์ดแวร์และระบบการทหารขนาดใหญ่ (ในบทความต้นฉบับ Royce เองได้เตือนถึงความจำเป็นของการวนย้อนกลับ แต่ในทางปฏิบัติอุตสาหกรรมมักนำรูปแบบเชิงเส้นตรงมาใช้)

โครงสร้างหลักแบ่งเป็นเฟสต่อเนื่องแบบน้ำตก 5–7 ขั้นตอน (Requirements Analysis & Definition → System & Software Design → Implementation & Unit Testing → Integration & System Testing → Operation & Maintenance) โดยมีเสาหลักสำคัญ 2 ประการ:

  • Phase Gates (Stage-Gate Control): ตามหลักการเชิงทฤษฎี เฟสที่ $N+1$ จะไม่สามารถเริ่มต้นได้จนกว่าเฟสที่ $N$ จะเสร็จสมบูรณ์และผ่านการอนุมัติอย่างเป็นทางการ
  • Document-Driven (ขับเคลื่อนด้วยเอกสาร): ผลผลิตหลักของทุกเฟสก่อนการเขียนโค้ดคือเอกสารที่ต้องลงนามรับรอง (Sign-off) เช่น เอกสาร SRS, เอกสารสถาปัตยกรรม SDD เพื่อใช้เป็นหลักฐานตรวจสอบความก้าวหน้าและอ้างอิงตามสัญญา

2.2 V-Model: การจัดแนวระหว่างการพัฒนาและการทดสอบ (Development & Testing Alignment)

V-Model (Sommerville Fig. 2.7) เป็นการต่อยอด Waterfall Model เพื่อแก้จุดอ่อนที่มักมองข้ามการวางแผนทดสอบจนถึงท้ายโครงการ โดยจัดเรียงขั้นตอนเป็นรูปตัว V: ฝั่งซ้าย คือกระบวนการย่อยรายละเอียดจากภาพรวมสู่ระดับโมดูล (Decomposition & Design) และ ฝั่งขวา คือกระบวนการประกอบและทดสอบย้อนกลับขึ้นไป (Integration & Verification) หัวใจสำคัญคือ Test Plans ของแต่ละระดับจะถูกเขียนขึ้นคู่ขนานทันทีในฝั่งซ้าย เพื่อสร้างความเชื่อมโยงตรงกัน 1 ต่อ 1

แผนภาพที่ 2.1: โครงสร้าง V-Model แสดงการจัดแนว Test Plans ในฝั่งซ้ายให้สอดคล้องกับการทดสอบในฝั่งขวา (ดัดแปลงจาก Sommerville Fig. 2.7)

2.3 บริบทที่เหมาะสมสำหรับ Traditional / Plan-Driven Models

แม้โมเดลแบบดั้งเดิมจะถูกวิพากษ์วิจารณ์ว่าขาดความยืดหยุ่น แต่ Sommerville (2016) ย้ำว่าโมเดล Plan-Driven ยังคงเป็นทางเลือกที่ดีที่สุดใน 4 สถานการณ์สำคัญ:

1. Safety-Critical Systems

Zero-Tolerance

ระบบที่ความผิดพลาดหมายถึงชีวิตหรือหายนะ เช่น ระบบควบคุมการบิน (Avionics) ระบบควบคุมรถไฟ หรือเครื่องปั๊มอินซูลิน ซึ่งต้องวิเคราะห์ความปลอดภัย (Hazard Analysis) และสร้าง Safety Case อย่างสมบูรณ์ก่อนลงมือเขียนโค้ด

2. Hardware-Software Co-Design

Embedded

ระบบฝังตัวที่ต้องรอผลิตฮาร์ดแวร์ควบคู่กันหรือฝังลงใน ROM (เช่น กล่อง ECU รถยนต์) การเปลี่ยนแปลงฟังก์ชันซอฟต์แวร์ภายหลังมีราคาแพงมาก จึงต้องล็อก Interface ทางฮาร์ดแวร์ล่วงหน้า

3. Multi-Partner Large Engineering

Contractual

โครงการขนาดมหึมาที่มีหลายบริษัทรับเหมาพัฒนา Subsystem แยกกัน (ต่างสถานที่/ต่างองค์กร) เอกสาร Complete Specification เป็นตัวกลางสำคัญเพื่อให้แต่ละทีมทำงานขนานกันได้

4. Regulatory Compliance

Auditability

อุตสาหกรรมที่มีกฎหมายหรือหน่วยงานกำกับดูแลเข้มงวด เช่น FDA (เครื่องมือแพทย์), DO-178C (การบิน), Sarbanes-Oxley (บัญชี) ซึ่งบังคับต้องมีเอกสาร Traceability ย้อนหลังครบทุกขั้นตอน

2.4 ข้อจำกัดเชิงลึกและจุดคอขวดของโมเดลแบบดั้งเดิม

เมื่อนำ Waterfall ไปใช้กับซอฟต์แวร์ธุรกิจทั่วไปที่มีความไม่แน่นอนสูง จะเกิดจุดคอขวดเชิงโครงสร้าง 5 ประการ:

  1. Big Design Up Front (BDUF) และ Premature Freezing: การบังคับให้ระบุความต้องการและออกแบบสถาปัตยกรรมทั้งหมด 100% ตั้งแต่วันแรกทั้งที่ผู้ใช้ยังไม่เห็นภาพจริง เมื่อลูกค้าหรือผู้พัฒนาเร่งรีบปิดจบเฟส Requirements ("แช่แข็ง Spec ก่อนเวลาอันควร") ปัญหาจะถูกซุกไว้ใต้พรมและบีบให้โปรแกรมเมอร์ต้องเขียนโค้ดแฮ็ก (Workarounds) ในเฟสหลังจนสถาปัตยกรรมพัง
  2. The Waterfall Dilemma (Dooley & Kazakova, 2024): สรุปเป็น 2 ปัญหาใหญ่ที่แก้ไม่ตก คือ Problem 1: ต้องจบเฟส N ก่อนจึงจะเริ่มเฟส N+1 ได้ และ Problem 2: ไม่มีกลไกย้อนกลับไปปรับปรุงเฟสก่อนหน้าอย่างคุ้มค่า เพราะในความเป็นจริง ซอฟต์แวร์เป็น "Wicked Problem" (ปัญหาที่ผู้มีส่วนได้ส่วนเสียจะเข้าใจความต้องการที่แท้จริงได้ก็ต่อเมื่อได้เห็นหรือลองใช้ตัวระบบแล้วเท่านั้น)
  3. Late Integration Risk: ช่วงเวลาส่วนใหญ่ในเฟสต้นหมดไปกับเอกสารและการเขียนโมดูลแยกส่วน การประกอบระบบจริง (Integration) ถูกเลื่อนไปท้ายโครงการ ทำให้บั๊กเชิงสถาปัตยกรรม คอขวดด้านประสิทธิภาพ และความไม่เข้ากันของ API เพิ่งโผล่ออกมาในช่วงที่เวลาและงบประมาณใกล้หมด
  4. Handoff Friction (แรงเสียดทานจากการส่งต่อข้ามไซโล): เมื่อทีมถูกแบ่งตามหน้าที่ (Analyst → Architect → Programmer → QA) การส่งต่อผ่านเอกสารหนาหนักมักเกิดการสูญหายของบริบท (Knowledge Loss) และการโยนความรับผิดชอบเมื่อเกิดปัญหา
  5. Defect Amplification & Cost of Change Curve: ความผิดพลาดที่เกิดในเฟส Requirements หากตรวจพบทันทีจะแก้ได้ด้วยต้นทุนต่ำมาก แต่หากปล่อยให้ไหลผ่าน Design และ Coding ไปพบในเฟส Testing หรือหลังส่งมอบ (Production) ค่าใช้จ่ายในการรื้อสถาปัตยกรรม แก้โค้ด ทดสอบใหม่ และชดเชยความเสียหายทางธุรกิจจะพุ่งสูงขึ้นแบบทวีคูณ (Exponential Escalation)

กราฟเปรียบเทียบต้นทุนการแก้ไขข้อผิดพลาด (Cost of Change Escalation Curve)

Relative Cost Multiplier

Iterative & Incremental Process Models — โมเดลแบบทำซ้ำ เพิ่มพูน และบริหารความเสี่ยง

ทำความเข้าใจทางออกจากข้อจำกัดของ Waterfall ด้วยการแบ่งส่งมอบและการทำซ้ำ แยกแยะความต่างระหว่าง Iterative, Incremental, Throwaway/Evolutionary Prototyping และเจาะลึก Spiral Model แบบ 4 Quadrants ของ Barry Boehm

3.1 นิยามและการเปรียบเทียบเชิงลึกระหว่าง Iterative vs. Incremental Development

คำว่า Iterative และ Incremental มักถูกใช้คู่กันจนสับสน แต่ในทางวิศวกรรมซอฟต์แวร์ทั้งสองแนวคิดมีเป้าหมายเชิงกลยุทธ์ที่ต่างกันชัดเจน:

มิติการเปรียบเทียบ Iterative Development (ทำซ้ำ/ขัดเกลา) Incremental Development (เพิ่มพูนทีละส่วน) Combined Iterative & Incremental
หลักการแกนกลาง สร้างโครงร่างระบบทั้งหมดหรือส่วนใหญ่แบบคร่าวๆ ก่อน แล้ววนรอบปรับปรุงคุณภาพ ความแม่นยำ และ UX ให้ดีขึ้นเรื่อยๆ แบ่งระบบออกเป็นส่วนย่อย (Increments) ตามลำดับความสำคัญ แล้วพัฒนาส่งมอบทีละส่วนจนครบสมบูรณ์ พัฒนาทีละส่วนที่ใช้งานได้จริง พร้อมเปิดรับ Feedback เพื่อกลับไปขัดเกลาส่วนเดิมและวางแผนส่วนถัดไป
อุปมาเชิงศิลปะ การวาดภาพสเก็ตช์ทั้งผืนผ้าใบแล้วค่อยๆ ลงสีและเก็บรายละเอียดให้คมชัดทั้งภาพ การต่อจิ๊กซอว์ทีละชิ้นที่สมบูรณ์แล้ว จนครบเป็นภาพใหญ่ วาดทีละโซนให้สมบูรณ์พอใช้งานได้ แล้วปรับแสงเงาทั้งภาพทุกรอบ
จุดแข็งหลัก ลดความเสี่ยงด้านความเข้าใจผิดใน Requirements และสถาปัตยกรรม ส่งมอบคุณค่าทางธุรกิจ (Early Value) ได้เร็ว ลดต้นทุนการแก้ความต้องการ (Sommerville 2.1.2) ได้ทั้งความเร็วในการส่งมอบและความยืดหยุ่นในการปรับคุณภาพ (เป็นรากฐานของ Agile)
ข้อควรระวัง อาจใช้เวลานานก่อนผู้ใช้จะได้ระบบที่นำไปใช้งานจริงได้ ต้องวางสถาปัตยกรรมแกนกลาง (Common Facilities) ให้รองรับการต่อขยาย หากขาดวินัยในการ Refactoring โครงสร้างโค้ดจะเสื่อมโทรม (Structural Degradation)

Incremental Development vs. Incremental Delivery และปัญหาการบริหารจัดการ

Sommerville (บทที่ 2.1.2 & 2.3.2) แยกแยะว่า Incremental Development คือการพัฒนาเป็นรอบๆ เพื่อนำไปสาธิตให้ผู้มีส่วนได้ส่วนเสียดู แต่ไม่จำเป็นต้องติดตั้งใช้งานจริงทุกรอบ ส่วน Incremental Delivery คือการนำ Increment ที่มีลำดับความสำคัญสูงสุดไปติดตั้งในสภาพแวดล้อมการทำงานจริงของลูกค้า (Production) เพื่อรับ Feedback จากการใช้งานจริง ซึ่งช่วยหลีกเลี่ยงการปักใจล็อก Spec ทั้งระบบตั้งแต่ต้น

2 ปัญหาหลักด้านการบริหารจัดการของ Incremental Development (Sommerville 2.1.2)
  • 1. Process Visibility (การมองเห็นความก้าวหน้า): ผู้บริหารต้องการเอกสาร Deliverable ประจำระยะเพื่อวัดผล แต่การพัฒนาแบบรวดเร็วไม่คุ้มค่าที่จะเขียนเอกสารประกอบครบทุกเวอร์ชันย่อย
  • 2. System Structure Degradation (ความเสื่อมโทรมของโครงสร้างระบบ): การเพิ่มฟีเจอร์ใหม่อย่างต่อเนื่องมักทำให้โค้ดยุ่งเหยิงและเปราะบาง ทางแก้จำเป็นต้องมีวินัยในการทำ Refactoring (ปรับโครงสร้างโค้ดโดยไม่เปลี่ยนพฤติกรรม) อย่างสม่ำเสมอ นอกจากนี้ระบบขนาดใหญ่มากหรือระบบที่ต้องทดแทนระบบเดิมทั้งหมด (Legacy Replacement) มักใช้ Incremental Delivery ล้วนได้ยาก เพราะผู้ใช้ไม่ยอมใช้ระบบใหม่ที่ฟีเจอร์ยังไม่ครบเท่าระบบเก่า

3.2 Prototyping Models: Throwaway vs. Evolutionary Prototyping

System Prototyping คือการสร้างตัวแบบจำลองของระบบอย่างรวดเร็วเพื่อใช้ทดลองร่วมกับผู้ใช้และทดสอบความเป็นไปได้ของการออกแบบ (Change Anticipation — ลดการขอแก้ไข Spec หลังส่งมอบ) โมเดลนี้แบ่งออกเป็น 2 สายหลักที่ห้ามนำมาปะปนกัน:

หัวข้อเปรียบเทียบ Throwaway (Exploratory) Prototyping Evolutionary Prototyping
เป้าหมายหลัก ค้นหาความต้องการที่แท้จริง (Requirements Validation) หรือพิสูจน์ Feasibility ทางเทคนิคในส่วนที่เสี่ยงสูง ส่งมอบระบบที่ใช้งานได้จริงตั้งแต่ต้น แล้วค่อยๆ ขยายและวิวัฒนาการตัวแบบนั้นไปเป็นระบบ Production
คุณภาพโค้ดเริ่มต้น เน้นความเร็วเป็นหลัก อาจละเลย Error Handling, Security, หรือ Clean Architecture เพราะตั้งใจ "ทิ้ง" เมื่อได้คำตอบ ต้องวางโครงสร้างสถาปัตยกรรม คุณภาพโค้ด และความปลอดภัยให้แข็งแรงตั้งแต่ก้าวแรก
ความเสี่ยงร้ายแรง ผู้บริหารหรือลูกค้าเห็น Prototype ทำงานได้แล้วสั่งให้นำไปขึ้น Production ทันที (กลายเป็น Code-and-Fix Anti-pattern ที่บำรุงรักษาไม่ได้) หากความต้องการหลักเปลี่ยนแบบถอนรากถอนโคนกลางทาง การปรับสถาปัตยกรรมอาจทำได้ยาก

3.3 Spiral Model: กรอบการทำงานแบบขับเคลื่อนด้วยความเสี่ยง (Risk-Driven 4 Quadrants)

3.4 การบริหารจัดการความต้องการที่ไม่แน่นอนและความเสี่ยง (Handling Uncertain & Evolving Requirements)

ในการพัฒนาซอฟต์แวร์จริง ความต้องการเปลี่ยนแปลงตลอดเวลาเนื่องจากสภาพตลาด กฎหมาย และความเข้าใจที่เพิ่มขึ้นของผู้ใช้ Sommerville (บทที่ 2.3) และ Dooley & Kazakova (บทที่ 2) เสนอกลยุทธ์การรับมือความไม่แน่นอน 3 ประการ:

  • Change Anticipation (คาดการณ์การเปลี่ยนแปลงล่วงหน้า): ใช้ Throwaway Prototyping หรือ UX Mockups เพื่อให้ผู้ใช้ทดลองก่อนเขียนโค้ดจริง ลดการขอแก้หลังส่งมอบ
  • Change Tolerance (ออกแบบกระบวนการให้ทนทานต่อการเปลี่ยนแปลง): ใช้การพัฒนาแบบ Incremental Delivery และการวางสถาปัตยกรรมแบบ Modular / Loose Coupling เพื่อให้ปรับแก้เฉพาะจุดได้ในต้นทุนต่ำ
  • MVP-Based Closed-End Mini-Projects (Dooley & Kazakova): แบ่งโครงการใหญ่เป็นรอบย่อยที่มีเป้าหมายชัดเจนเป็น Minimum Viable Product (MVP) ซึ่งแต่ละรอบต้องมีเกณฑ์ความสำเร็จแบบ Binary (Done / Not Done) สามารถ Demo เพื่อเก็บ Feedback มาปรับแผนรอบถัดไปได้ทันที

4.1 ปรัชญา Agile Manifesto (4 Core Values, 12 Principles) และ Lean Software Development

ในช่วงปลายทศวรรษ 1990s วิศวกรซอฟต์แวร์กลุ่มหนึ่งเกิดความไม่พอใจกับกระบวนการแบบ Plan-Driven ที่หนักเอกสาร (Heavyweight) จนทีมใช้เวลาเขียนเอกสารและประชุมอนุมัติมากกว่าเขียนโค้ด จึงร่วมกันประกาศ Agile Manifesto (2001) เพื่อวางค่านิยมหลัก 4 ประการ (โดยตระหนักว่าฝั่งขวามีคุณค่า แต่ให้คุณค่าฝั่งซ้ายมากกว่า):

Value 01

People

Individuals and interactions over processes and tools — ให้ความสำคัญกับคนและการสื่อสารโดยตรงมากกว่าขั้นตอนตายตัวและเครื่องมือ

Value 02

Software

Working software over comprehensive documentation — ซอฟต์แวร์ที่ทำงานได้จริงเป็นตัววัดความก้าวหน้าหลัก เหนือกว่าเอกสารที่หนาเทอะทะ

Value 03

Collaboration

Customer collaboration over contract negotiation — ร่วมมือกับลูกค้าอย่างใกล้ชิดระหว่างพัฒนา แทนการถกเถียงตีความตามตัวอักษรในสัญญา

Value 04

Adaptability

Responding to change over following a plan — พร้อมปรับตัวรับความเปลี่ยนแปลง ดีกว่ายึดติดกับแผนเดิมที่ล้าสมัยไปแล้ว

สรุป 12 Principles ของ Agile (จัดกลุ่มเป็น 4 เสาหลัก)

  • Customer Value & Adaptability: ส่งมอบซอฟต์แวร์ที่มีคุณค่าอย่างรวดเร็วและต่อเนื่อง (ข้อ 1) และยินดีต้อนรับการเปลี่ยนแปลงของความต้องการแม้ในช่วงท้ายของการพัฒนา (ข้อ 2)
  • Frequent Iterative Delivery: ส่งมอบซอฟต์แวร์ที่ทำงานได้ทุกๆ 2–3 สัปดาห์หรือ 1–2 เดือน (ข้อ 3) โดยใช้ Working Software เป็นตัวชี้วัดหลัก (ข้อ 7)
  • Empowered Cross-Functional Teams: ฝ่ายธุรกิจและนักพัฒนาทำงานร่วมกันทุกวัน (ข้อ 4), สร้างสภาพแวดล้อมที่ไว้ใจทีม (ข้อ 5), สื่อสารแบบ Face-to-face (ข้อ 6), รักษาจังหวะการทำงานที่ยั่งยืน (ข้อ 8), และทีมจัดการตนเอง (ข้อ 11)
  • Technical Excellence & Simplicity: ใส่ใจความเป็นเลิศทางเทคนิคและการออกแบบที่ดีอย่างต่อเนื่อง (ข้อ 9), ความเรียบง่ายคือการตัดงานที่ไม่จำเป็นทิ้ง (ข้อ 10), และทบทวนปรับปรุงทีมสม่ำเสมอ (ข้อ 12)

Lean Software Development: การกำจัดความสูญเปล่า 7 ประการ (7 Wastes)

Mary & Tom Poppendieck (2003) และ Dooley & Kazakova (2024) นำแนวคิด Lean Manufacturing มาประยุกต์กับซอฟต์แวร์ โดยระบุ ความสูญเปล่า (Waste / Muda) ที่ต้องกำจัดให้หมดไป ได้แก่: (1) Partially Done Work (โค้ดที่เขียนไว้แต่ยังไม่ Test/ยังไม่ Deploy), (2) Extra Processing (เอกสารส่วนเกิน การประชุมที่ไม่จำเป็น), (3) Extra Features (ฟีเจอร์ที่ไม่มีใครใช้ — Gold Plating), (4) Task / Context Switching (การให้คนหนึ่งคนสลับทำหลายโปรเจกต์พร้อมกัน), (5) Waiting (รอการอนุมัติ รอโค้ดจากทีมอื่น), (6) Motion (การส่งต่อข้อมูลข้ามหลายคนโดยไม่มีระบบจัดเก็บที่ชัดเจน), และ (7) Defects (บั๊กที่หลุดรอดไปจนแก้ยากและแพง)

4.2 Scrum Framework: Roles, Artifacts & Events

Scrum (Sommerville Ch. 3.3) เป็นกรอบการทำงานแบบ Agile ที่ได้รับความนิยมสูงสุด จัดระเบียบงานผ่านรอบเวลาคงที่เรียกว่า Sprint (ปกติ 1–4 สัปดาห์) ประกอบด้วย 3 บทบาท (Accountabilities), 3 ชิ้นงาน (Artifacts) และ 5 กิจกรรม (Events)

องค์ประกอบ Scrum รายละเอียดและหน้าที่รับผิดชอบ ข้อผูกมัด / จุดเน้นสำคัญ
Role 1: Product Owner (PO) ผู้บริหารจัดการ Product Backlog กำหนดทิศทางและจัดลำดับความสำคัญของงานตามคุณค่าทางธุรกิจ เป็นตัวแทนเสียงของลูกค้า ความรับผิดชอบสูงสุดต่อผลตอบแทนคุณค่าของผลิตภัณฑ์ (Value Maximization)
Role 2: Scrum Master (SM) Servant Leader ผู้ช่วยให้ทีมเข้าใจและปฏิบัติตามหลัก Scrum ขจัดอุปสรรค (Impediments) และปกป้องทีมจากการแทรกแซงระหว่าง Sprint ไม่ใช่หัวหน้างานแบบสั่งการ (Not a traditional PM) แต่เป็น Process Coach
Role 3: Developers ทีมข้ามสายงาน (Cross-functional) ที่ร่วมกันออกแบบ เขียนโค้ด ทดสอบ และส่งมอบ Increment ในทุก Sprint มีอำนาจในการจัดสรรงานและประเมินขนาดงานด้วยตนเอง (Self-managing)
Artifact 1: Product Backlog รายการความต้องการทั้งหมดของระบบที่เรียงลำดับความสำคัญจากบนลงล่าง และปรับปรุงตลอดเวลา Commitment: Product Goal (เป้าหมายระยะยาวของผลิตภัณฑ์)
Artifact 2: Sprint Backlog ชุด Product Backlog Items ที่ทีมเลือกมาทำใน Sprint ปัจจุบัน พร้อมแผนการปฏิบัติงาน (Tasks) Commitment: Sprint Goal (เป้าหมายรวมของ Sprint นี้)
Artifact 3: Increment ผลรวมของชิ้นงานที่เสร็จสมบูรณ์ ใช้งานได้จริง และผสานเข้ากับชิ้นงานก่อนหน้าอย่างสมบูรณ์ Commitment: Definition of Done (DoD) (เกณฑ์มาตรฐานคุณภาพ เช่น ผ่าน Test & Review แล้ว)

5 กิจกรรม Time-Boxed ของ Scrum

  • 1. The Sprint: ภาชนะบรรจุเวลา 1–4 สัปดาห์ที่ห้ามเปลี่ยนแปลงเป้าหมายหลักกลางคันเพื่อให้เกิดสมาธิในการส่งมอบ Increment
  • 2. Sprint Planning: วางแผน 3 เรื่อง คือ Why (กำหนด Sprint Goal), What (PO และทีมเลือก Backlog Items), และ How (Developers แตกงานเป็น Tasks)
  • 3. Daily Scrum: ประชุมยืน 15 นาทีทุกวันโดย Developers เพื่อตรวจสอบความคืบหน้าสู่ Sprint Goal และระบุปัญหาติดขัด (ไม่ใช่การรายงานหัวหน้างาน)
  • 4. Sprint Review: ท้าย Sprint ทีมสาธิต Working Increment ให้ Stakeholders ทดลองใช้งานจริงและเก็บ Feedback เพื่อปรับ Product Backlog
  • 5. Sprint Retrospective: ทีมทบทวนกระบวนการทำงานภายใน (People, Process, Tools, DoD) เพื่อหา Action Item ปรับปรุงให้ Sprint หน้าดียิ่งขึ้น

4.3 Kanban Method: 6 Core Practices, WIP Limits & Flow Management

Kanban มุ่งเน้นการส่งมอบงานอย่างต่อเนื่อง (Continuous Flow) โดยไม่ต้องรอครบรอบ Sprint มีหลักปฏิบัติหลัก 6 Core Practices ได้แก่: (1) Visualize the Workflow (แสดงสถานะงานทั้งหมดบนบอร์ดให้เห็นคอขวด), (2) Limit Work in Progress (WIP) (จำกัดจำนวนงานที่ทำค้างไว้ในแต่ละคอลัมน์), (3) Manage Flow (วัดและปรับปรุงความลื่นไหลของงาน), (4) Make Process Policies Explicit (เขียนกฎการย้ายคอลัมน์ให้ทุกคนรู้ตรงกัน), (5) Implement Feedback Loops (ทบทวน Flow และบริการ), และ (6) Improve Collaboratively (พัฒนาด้วยข้อมูลเชิงประจักษ์)

Little's Law และความต่างระหว่าง Lead Time กับ Cycle Time

หัวใจทางคณิตศาสตร์ของ Kanban คือ Little's Law: Average Lead Time = WIP / Throughput ดังนั้นวิธีลดระยะเวลารอคอยที่ทรงพลังที่สุดไม่ใช่การเร่งให้คนทำงานหนักขึ้น แต่คือ การลด WIP Limit เพื่อให้ทีมโฟกัสปิดงานทีละชิ้น ลด Context Switching (Stop starting, start finishing!)

  • Lead Time: เวลาทั้งหมดตั้งแต่การ์ดงานถูกสร้าง/รับเข้ามาในระบบ (Requested) จนถึงเวลาที่ส่งมอบเสร็จสมบูรณ์ (Delivered/Done) — มุมมองของลูกค้า
  • Cycle Time: เวลาตั้งแต่ทีมวิศวกรเริ่มลงมือทำจริง (In Progress) จนถึงเสร็จสิ้น (Done) — มุมมองประสิทธิภาพของทีมพัฒนา

5.1 การจัดโครงสร้างทีมและวัฒนธรรมใน Software House

ใน Software House สมัยใหม่ ประสิทธิภาพของการส่งมอบไม่ได้ขึ้นอยู่กับความเก่งรายบุคคลเท่านั้น แต่ขึ้นอยู่กับการออกแบบโครงสร้างทีมและสภาพแวดล้อมทางสังคมของวิศวกร:

  • Cross-Functional Team (ทีมข้ามสายงาน): แทนที่จะแยกแผนก Frontend, Backend, QA และ Ops ออกจากกัน (ซึ่งสร้าง Handoff Friction และเวลารอคอย) ทีมผลิตซอฟต์แวร์ยุคใหม่รวมทุกทักษะที่จำเป็นไว้ในทีมเดียว (5–9 คน) เพื่อให้จบงานได้ตั้งแต่ต้นจนขึ้น Production (End-to-End Ownership)
  • Psychological Safety (ความปลอดภัยทางจิตใจ): งานวิจัย Project Aristotle ของ Google และ Amy Edmondson พบว่าปัจจัยอันดับหนึ่งของทีมประสิทธิภาพสูงคือความเชื่อมั่นว่าสมาชิกสามารถตั้งคำถาม ขอความช่วยเหลือ เสนอไอเดียแย้ง หรือยอมรับความผิดพลาดได้โดยไม่ถูกลงโทษหรืออับอาย นำไปสู่วัฒนธรรม Blameless Post-mortem (เมื่อระบบล่ม ให้วิเคราะห์จุดอ่อนของกระบวนการและเครื่องมือ ไม่ใช่หาแพะรับบาป)
  • Soft-Aware Development & Sociotechnical Mindset: อ้างอิงแนวคิด Sociotechnical Systems ของ Sommerville (บทที่ 10 & 19) วิศวกรต้องตระหนักว่าซอฟต์แวร์เป็นส่วนหนึ่งของระบบสังคมและองค์กร ต้องคำนึงถึงจรรยาบรรณ (ACM/IEEE Code of Ethics) กฎหมายข้อมูลส่วนบุคคล ความหลากหลายของผู้ใช้ และความยืดหยุ่นทางสังคมควบคู่ไปกับโค้ด

5.2 ระบบ Issue Tracking และการประยุกต์ใช้ GitHub Projects / Jira

ระบบ Issue Tracking อย่าง GitHub Projects หรือ Jira ทำหน้าที่เป็น Single Source of Truth ของทีม เพื่อให้มองเห็นงานทั้งหมด (Work Visualization) และเชื่อมโยงความต้องการเข้ากับโค้ดจริง:

  • ลำดับชั้นของงาน (Work Hierarchy): Milestone / Initiative (เป้าหมายรุ่นส่งมอบ) → Epic (ฟีเจอร์กลุ่มใหญ่) → User Story / Issue (งานที่ส่งมอบคุณค่าได้ใน 1 Sprint) → Sub-task / Checklist (งานย่อยทางเทคนิค)
  • องค์ประกอบสำคัญบน Board: การตั้งสถานะที่สะท้อน Workflow จริง (เช่น Backlog → Ready → In Progress [WIP: 3] → In Review → Done), การติด Labels (feat, bug, tech-debt, blocked) และ Custom Fields สำหรับบันทึก Story Points และ Iteration/Sprint
  • Traceability อัตโนมัติ: ใน GitHub Projects เมื่อนักพัฒนาผูก Issue ID เข้ากับ Pull Request (เช่น Closes #42) สถานะการ์ดบน Board จะขยับจาก In Progress ไปยัง In Review และ Done โดยอัตโนมัติ ลดภาระงานเอกสารซ้ำซ้อน

5.3 Version Control Workflows & Git Branching Strategies

Configuration Management & Distributed Version Control (Sommerville Ch. 25) เป็นเสาหลักของการทำงานร่วมกัน ระบบ Git ช่วยให้วิศวกรทุกคนมี Repository ฉบับเต็มและทำงานขนานกันได้โดยไม่ทับซ้อนกันผ่านกลยุทธ์ Branching ที่เหมาะสม:

กลยุทธ์ Branching โครงสร้าง Branch หลัก จุดแข็ง & บริบทที่เหมาะสม
GitHub Flow (Feature Branching) main (พร้อม Deploy ตลอดเวลา) + feature/* หรือ fix/* แตกจาก main แล้ว Merge กลับผ่าน PR เรียบง่าย รวดเร็ว เหมาะกับเว็บแอปพลิเคชัน SaaS ที่ใช้ CI/CD ปล่อยงานบ่อย และ Senior Project
GitFlow main, develop, feature/*, release/*, hotfix/* รองรับการดูแลซอฟต์แวร์หลายเวอร์ชันพร้อมกัน (เช่น Mobile Apps หรือซอฟต์แวร์องค์กรที่มีรอบ Release ชัดเจน)
Trunk-Based Development ทุก Commit เข้า main (Trunk) บ่อยครั้ง (หรือ Short-lived branch ไม่เกิน 1–2 วัน) ใช้ Feature Flags ลด Merge Conflict สูงสุด เหมาะกับทีมระดับสูงที่มี Automated Test Coverage เข้มแข็ง

Pull Requests (PRs), Code Review Culture & Branch Protection: Pull Request ไม่ใช่แค่คำสั่งรวมโค้ด แต่เป็นจุดทำ Static Verification ที่ทรงพลังที่สุด การสร้างวัฒนธรรม Code Review ที่ดีควรตรวจทั้ง Logic, Security, Readability และ Test Coverage โดยให้คำแนะนำอย่างสร้างสรรค์ ("วิจารณ์โค้ด ไม่วิจารณ์คน") พร้อมตั้งกฎ Branch Protection Rules บน Branch main ได้แก่ (1) ห้าม Push ตรงเข้า main, (2) ต้องผ่าน PR และได้รับการอนุมัติอย่างน้อย 1–2 คน, และ (3) Status Checks จาก CI Pipeline ต้องผ่านทั้งหมดก่อน Merge

5.4 Modern Engineering: CI/CD Pipelines, Automated Testing & Process Metrics

CI/CD Pipelines (Continuous Integration / Delivery / Deployment): ทุกครั้งที่มีการ Push หรือเปิด PR ระบบ CI (เช่น GitHub Actions) จะทำงานอัตโนมัติ: Checkout Code → Install Dependencies → Linter/Static Analysis → Run Automated Tests → Build Artifact หากผ่านทั้งหมดและ Merge แล้ว ระบบ Continuous Delivery จะนำขึ้น Staging เพื่อตรวจรับ หรือ Continuous Deployment จะส่งขึ้น Production อัตโนมัติทันที

Automated Testing Pyramid & TDD: การทดสอบอัตโนมัติควรมีฐานล่างเป็น Unit Tests จำนวนมาก (รันเร็ว ทดสอบฟังก์ชัน/คลาสแยกเดี่ยว) ชั้นกลางเป็น Integration / API Tests และยอดบนเป็น End-to-End (E2E) Tests ในจำนวนที่พอเหมาะ นอกจากนี้เทคนิค Test-Driven Development (TDD — Sommerville 8.2) ที่เขียนเทสต์ให้ Fail ก่อน (Red) → เขียนโค้ดให้ผ่านเทสต์ (Green) → ปรับโครงสร้างให้สะอาด (Refactor) ช่วยให้เกิด Regression Safety Net ตลอดชีวิตซอฟต์แวร์

Process Metrics สำหรับติดตามและปรับปรุงทีม:

  • Velocity: จำนวน Story Points ที่ทีมทำเสร็จ (ตรงตาม DoD) ในแต่ละ Sprint ใช้สำหรับพยากรณ์กำลังการผลิตใน Sprint ถัดไป (ข้อห้ามสำคัญ: ห้ามใช้ Velocity เปรียบเทียบระหว่างทีมหรือประเมินผลงานรายบุคคล เพราะจะเกิดการปั่นตัวเลข Story Points!)
  • Sprint Burn-down & Release Burn-up Charts: Burn-down แสดงงานคงเหลือเทียบกับเวลาที่เหลือใน Sprint ส่วน Burn-up แสดงงานที่เสร็จสะสมเทียบกับเส้น Total Scope ซึ่งช่วยแยกแยะได้ชัดว่าความล่าช้าเกิดจากทีมทำช้าหรือเกิดจาก Scope Creep
  • Cumulative Flow Diagram (CFD): กราฟพื้นที่สะสมที่แสดงจำนวนงานในแต่ละสถานะตามแกนเวลา สามารถอ่านค่าสำคัญได้ทันที: ความสูงแนวตั้งระหว่างเส้น = ปริมาณ WIP, ระยะห่างแนวนอน = Average Lead/Cycle Time, และ ความชันของแถบ Done = Throughput หากแถบใดพองตัวขึ้นแสดงว่ากำลังเกิดคอขวด (Bottleneck) ที่สถานะนั้น

แปลงฟังก์ชันในบทที่ 1–3 ของ Senior Project เป็น GitHub Issues โดยระบุรูปแบบ User Story และ Acceptance Criteria ให้ชัดเจน ใช้การโหวต Planning Poker ประเมิน Story Points และจัดลำดับความสำคัญร่วมกับอาจารย์ที่ปรึกษา (สวมบทบาท PO/Stakeholder)

04

เปิดใช้งาน Branch Protection และ GitHub Flow

ล็อก Branch main (ห้าม Direct Push, บังคับ PR + 1 Reviewer Approval + CI Pass) สมาชิกทุกคนแตกสาขาใหม่ตามเลข Issue เช่น feat/14-auth-login หรือ fix/23-pdf-export และเขียน Commit Message แบบ Conventional Commits

05

ดำเนิน Sprint รอบละ 1–2 สัปดาห์ และทำ Code Review จริงจัง

จัด Daily/Async Check-in บนแชทหรือบอร์ด 15 นาที แจ้งงานที่ทำและอุปสรรค (Blocker) เมื่อโค้ดเสร็จให้เปิด PR พร้อมแนบ Screenshots/Test Result และอ้างอิง Closes #issue-id เพื่อให้เพื่อนร่วมทีมตรวจ Code Review ตาม Definition of Done

06

Sprint Review, Burn-down Check & Retrospective

ท้ายรอบ Sprint สาธิตซอฟต์แวร์จริงบน Staging/Demo (ห้ามโชว์แค่สไลด์) ตรวจสอบ Velocity และ Burn-down Chart ใน GitHub Insights แล้วทำ Retrospective (Start / Stop / Continue) เพื่อปรับปรุงกระบวนการทำงานใน Sprint ถัดไป
